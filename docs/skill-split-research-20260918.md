## 1. 元 Skill 是什么，我们是什么

**Skill 类型学（四分法）**：

| 类型 | 管什么 | 加载形态 | 验收面 | 本仓对应 |
|---|---|---|---|---|
| **元 Skill（治理层）** | agent 自身怎么干活——纪律/流程/判级/行为 | 必须每会话**在场**（触达是生死线） | **行为面**（遵循率，非功能） | **shisan-xinuo-workflow（就是这一类）** |
| 知识型 Skill | 领域知识/规范/参考 | description 触发按需读 | 内容正确性 | vercel-react-best-practices、cms-skill-collection |
| 工作者型 Skill | 完成具体任务（产出物） | description 触发 | 功能产出 | docx/pdf/pptx、scrollcraft、web-artifacts-builder |
| 角色型 Skill/Agent | 以特定身份审查/执行（身份×能力×维度×出口×路由） | 显式调度 | 结论质量 | critic/risk-reviewer/security-auditor 模板 |

**我们=典型元 Skill**。元 Skill 的四个特殊性直接决定拆分逻辑：
1. **触达>内容**：装了没被加载=0（本项目全部路测史的主题）；工作者 Skill 靠 description 触发即可，元 Skill 需要「每会话无条件在场」的承载（注入核心+hooks）。
2. **验收=行为面**：不能拿「功能跑通」验收，要拿探针测遵循率（3.0 loop 探针批先例）。
3. **天然膨胀倾向**：每个新坑都想立条（330→344 条的代谢史）——skill-creator 官方原话「模型因 skill 忙乱重读绕圈=skill 过度规定的信号，**该砍不该加**」正是元 Skill 的反膨胀判据。
4. **拆分形态不同**：工作者 Skill 拆多小没问题（清单成本线性、触发各管各）；**元 Skill 拆多小反而致命**——治理指令分裂在多个触发体里，「该遵循的纪律」会变成「恰好没被触发的 Skill」。社区共识「单职责小 Skill」对知识/工作者成立，对元 Skill 必须**修正为「常驻最小核心 + 按需引用细则」的内部拆分**，而非拆成多个独立 Skill。

## 2. 规范共识（可加载规范的第一方+社区口径）

- **官方（ZCode skill-creator 插件，Anthropic 规范的第一方承载；platform.claude.com 本机区域屏蔽，经此替代取证）**：
  - 三层渐进披露：元数据常驻（name+description 从短）→ SKILL.md 正文触发时加载（**目标 <500 行**）→ references/ scripts/ assets/ 按需（原则上不限量）。
  - description=首要触发信号，模型普遍**欠触发**——要写「推」一点（什么场景都该想到它，即使用户没点名）。
  - 正文变长→**拆 reference 文件，SKILL.md 指路**（"if target is AWS, read references/aws.md"）。
  - 写作=祈使句+**例胜于规**；全大写 MUST/NEVER 变多=规则缺解释的信号。
  - **过度规定检测**：skill 让模型忙乱（重读同文件/绕圈/一次性脚本）=over-prescribing，砍而非加。
- **社区**：「一个 skill 想干五件事，就会在错误时机触发」（Firecrawl）；心智模型二分 Knowledge vs Workers；mega vs modular 之争的实质=**触发可靠性（modular 优）vs 触达与维护面（mega 优）**——与 §1 元/工作者分治同构。
- **与本仓现状对照**：SKILL.md 正文 29,633 字符（≈700+ 行等效）**超官方目标线约 40-70%**；injection-core ≤6K 字符常驻（实测 ≈9.1K tok）；references/ 拆分形态**已符合**渐进披露规范（344 细则按症状 lookup 不预载）——**本仓的问题不是没拆，而是入口正文仍过厚 + 元/知识/角色三类混居一个包里**。

## 4. 拆分怎么做：方案空间（不做决定，供三轮对齐）

**拆分判据（从 §1-§3 推出）**：①元治理必须保持单触达面（常驻核心不分裂）②知识/角色/流程可外置为按需单元 ③每个外置单元要有「加载后行动契约」（触发确认/首动作/出口产物）④description 按官方「推开写」口径重写 ⑤清单成本守恒（外置单元数量克制，防 44 条目式膨胀复发）。

**候选结构（三案，代价并列）**：

| 案 | 形态 | 得 | 失 |
|---|---|---|---|
| A 单入口强化 | 保持 1 个 Skill；入口瘦到 <500 行官方线，细则/角色/流程全部下沉 references/（多数已在），入口只留路由表 | 触达面不变；发行面不变；改动最小 | 入口触发后仍整包加载 ~2 万 tok（利用率问题只解决一半） |
| B 双层（核心+工具箱） | 1 个极简元核心 Skill（纪律红线/判级/跑道入口，≤2K 字符常驻）+1 个流程包 Skill（九步细节/模板）+角色包 Skill（dispatch+模板，借 BMAD/Roo 形态） | 常驻最省；元/流程/角色分治清晰 | 3-4 个 Skill 清单行；跨包回指复杂度；发行面 ×3 |
| C 多 Skill 家族 | 按场景拆 5-8 个独立 Skill（git 包/测试包/前端包…） | 最贴合社区 modular 共识 | **元治理分裂风险**（§1.4）；清单膨胀复发；触达碎片化——**与本项目核心命题冲突，倾向排除** |

**无论哪案都做的共性动作**：入口正文瘦身到官方线；元/知识/工作者/角色四类内容显式标注归属；三对重复列示去重；零调用细则按利用率数据处置；dispatch 矩阵（症状→角色→出口契约）替代 SKILL §13 一行带过。

## 5. 三轮×五问对齐路线图与第一轮五问

路线：R1 需求与目标层（本轮）→ R2 方案取舍层（结构/预算/加载/必问边界）→ R3 施工与验收层（迁移/发行/探针判分）。R2/R3 题目将随 R1 答案生成，预注册于 agent-log 流水。

**第一轮五问（需求与目标对齐）**：

- **Q1 拆分的第一目标函数**（决定一切取舍）：拆分最想解决什么？A 行为遵循率/触达（规则在场但没人执行）B token 经济（每会话常驻与加载成本）C 维护代谢（344 条细则的增删改效率与膨胀控制）D 分发安装体验（他人下载后的上手门槛）——请排序或指主次。
- **Q2 元核心的常驻预算**：拆完后「每会话无条件在场」的部分（注入核心）可接受上限？现状 ≤6K 字符（实测 ≈9K tok）。A 压到 ≤3K 字符（更省但纪律压缩）B 维持 6K（只拆不压）C 不设字符线、以「行为面探针不回退」为验收。
- **Q3 版本与兼容策略**：v2.9.0 刚全渠道发行。A v3.0 破坏性重组（允许改判级/GATE/复述等在用契约，附迁移说明）B v2.x 渐进（对外契约冻结，只动文件组织与加载路径）C 先 A 案（单入口）试运行一个版本再决定是否 B。
- **Q4 角色包来源**：A 移植开源改造（BMAD persona/Roo modes/Claude subagents——能复用绝不自研）B 本仓三模板原地扩维（补 dispatch 矩阵+能力门控声明）C 混合（框架借开源、审查清单从本仓 344 细则本土化生成）。
- **Q5 实际实践痛点映射**（按你的纠正：不问理想流程，问实际）：你在「主控/并行/多分支」的实际操作里，当前最希望工作流接住的是哪些？A 多会话/多分支的状态接力与交接（#326 压缩接续一类）B 并行子代理的纪律下发与结果合并 C 主控长会话的上下文代谢（折叠/盘点）D 都不急，拆分不为这个设计。
