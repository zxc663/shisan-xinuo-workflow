# 一页纸：这个 Skill 是什么（简明版规范）

> 2026-09-23 立。目的：把散在六个文档里的定义收成一页——冷启动会话与外部读者先读这里，需要细则再按「证据在哪」索引展开。
> 术语消歧先说：行业里的 **product engineer** 通常指**一类人**（既做产品判断又写代码的工程师，"谁来做"）；本项目说的**产品工程**指**一套判据系统**（"什么叫做对"）。两者不冲突，但别混着读。

## 一句话

**产品工程 = 把「产品该有的都得有」翻译成「机器能检查」。**

每次会话的模型都是失忆的局部优化工人：写新代码最便宜、复用一个已有组件最贵、验证"做对没有"几乎没人做。这套 Skill 把工匠的三样东西外置给它——**地图**（项目里已有什么）、**厂规**（这个项目什么算对）、**验收机**（交付是不是真的做完了）。

## 它不是什么（三条边界）

1. **不是产品创新**——"该不该做、市场上有没有机会"属产品决策侧；本包管"既然决定做，它具体应该是什么"。
2. **不定义主题与组件**——组件注册表只当检查者（查"查没查、归因没归因"），不定义组件长什么样。
3. **不管审美手法与流程纪律**——好看归设计类 Skill，执行纪律归工作流；本包只回答"什么叫做对"。

## 它管什么（11 层，先定位再干活）

```
L0 产品目标      ← 只检查有没有被说明白，不替你想
L1 页面职责      ┐
L2 能力与功能    │  上游四层：该有的都有吗
L3 主次与完整性  │  （层级门必查段——没定就别往下走）
L4 运营/权限/数据┘
L5 信息架构      ← 本包未实现（诚实标注）
L6 交互  L7 状态 ← 本包核心：用户怎么完成、态怎么流转
L8 UI    L9 实现 ← 只守底线（a11y/归因）
L10 验证         ← 怎么证明做对了
```

**唯一的入口动作（层级门）**：先说出"这是哪一层的问题"→ 逐层向上检查上游有没有答案 → 没有就停下补，不许越级下沉。
例：有人问"这个按钮放左边还是右边"（L8）→ 先答"这个按钮对应的功能确认了吗？它在主次里是什么角色？"；有人要新建组件（L9）→ 先答"项目里是否已有承担同一职责的组件？"

## 怎么用（8 步跑道）

层级门（0a）→ 产品对象六问（0b，缺答=停）→ 功能面盘点 → 功能天生六问 → statechart → 承诺+六态矩阵 → 验收标准前置 → 实现（先查表）→ 验收三件（双向追溯/真证据/写回账本）。

**八台检查机（可重跑）**：`statechart-gate.py`（态机 C1-C7）｜`spec-trace-gate.py`（双向追溯）｜`registry-gate.py`（组件归因）｜`usage-probe.py`（使用率衰减警报）｜`product-object-gate.py`（产品对象 P1-P4）｜`l0-l5-gate.py`（L0 目标合格线+L5 结构底线）｜`frontend-lint-gate.py`（内联样式/硬编码色/console/空 catch）｜`a11y-gate.py`（可达性静态底线 A1-A4）。门禁均带 `--selftest`。
