# 三定义调研：产品 · 工程 · 产品工程

> 2026-09-23。触发：用户三问（产品究竟是什么／工程是什么／产品工程是什么）+ 三句候选定义（自述为「偏义纠正」）+ 对 2026 年 AI 落地的观察。
> 方法：①经典定义联网核证（出处 + 信心级）②行业用法核证（2025-2026 来源）③与本项目既有理论对齐（docs/direction.md §〇/§七/§九）。
> 结论：三句候选定义方向成立、逐级合成合理；三者共用一个缺陷——**定义的是结果态（名词+形容词），缺产生它的动作与判据（动词）**。本文给出加固版三定义，并把「缺失的逻辑」写成可工程化的表述。

## 0 结论（三定义 · 加固版）

- **产品 = 在约束下为他人制造、交付后需自行成立、以「声明范围内的闭合」为正确性判据的整体。**
  压缩成一句：产品问「**该有的是否都有**」。
- **工程 = 以可复算的证据，把「一次成立」变成「持续成立」，并为后续维护承担责任的约束→设计→验证→留证闭环；其稳定是「受控演化」的稳定。**
  压缩成一句：工程问「**已有的是否都对，且能否持续证明**」。
- **产品工程 = 把「完整性」翻译成「可判定性」的工程：让产品判据（该有的都得有）获得工程判据（可重跑命令 + 真实退出码）同等的可验证、可继承强度。**
  压缩成一句：产品工程 = **让第一个问题获得第二个问题的证据强度**。

三者关系：**产品是对象，工程是方法，产品工程是把「产品的正确性判据」翻译成「工程可判定的形式」的那道工序。**

## 1 产品究竟是什么

### 1.1 经典定义（出处）

- 科特勒/阿姆斯特朗（Kotler & Armstrong）《市场营销原理》：产品是「任何可以提供给市场，供注意、获取、使用或消费，并可能满足某种欲望或需要的东西」（"anything that can be offered to a market for attention, acquisition, use, or consumption that might satisfy a want or need"）。信心级：转述可靠（多个独立二级来源一致，未逐字核原书）。
- 产品五层次（核心利益 → 基础产品 → 期望产品 → 附加产品 → 潜在产品）：同一教材谱系。信心级：转述可靠。
- 要点：经典定义把产品的存在理由钉在**「他者需要」**上——产品不是为自己造的东西。这是全部后续讨论的地基。

### 1.2 产品的四个构成谓词（综合经典定义与工程实践）

1. **为他**（对象谓词）：为使用者而造，验收权在使用者，不在作者。
2. **交付**（边界谓词）：跨越作者→用户的边界后仍需成立。作者离场是产品的常态，不是意外。
3. **受限**（约束谓词）：在时间/成本/维护预算之内谈完整；无限完整不是产品，是幻想。
4. **闭合**（正确性谓词）：在**声明的使用范围**内，每条用户路径都有确定结局（成功/失败/恢复），没有悬空分支。
   ——「完整」只相对于一个范围声明存在；没有范围声明的「完整」不可判定。

### 1.3 产品的正确性判据=闭合：缺陷三级成本阶梯（核心推论一）

| 缺陷 | 例子 | 检出只需要 | 检出成本 |
|---|---|---|---|
| 代码 bug | 崩溃、异常、边界写错 | 一次运行或一个测试 | 低（局部可测） |
| 逻辑错误 | 条件写反、顺序错 | 一份规格（知道什么才对） | 中（规格必须存在且被对照） |
| **缺失逻辑** | 该有的分支/状态/出路/恢复不存在 | **规格自证完备**（知道「该有哪些」） | **高（缺口本身不产生任何信号）** |

关键性质：**错误是可观测的偏差；缺失是不可观测的偏差。**

- 工程手段（测试/监控/门禁）天然只对「存在的东西」起作用——测试跑的是写了的代码，门禁查的是写了的行。
- 所以缺失逻辑是纯工程手段的**系统性盲区**：它不报错、不崩、不红，只是安静地不存在。
- 用户原话「缺失的逻辑比错误的代码、错误的逻辑更可怕，你很难意识到」，其工程学表述就是上表：**检出缺失，要求判据本身完备**——这是三级阶梯里唯一一条需要「完备性判据」的。

### 1.4 对用户定义的裁决（产品）

| | 内容 |
|---|---|
| 用户定义 | 产品是一个完整整体 |
| 抓住的真属性 | **整体性**——产品不是部件的和；其正确性是整体的（缺一块不是 90%，是断了） |
| 偏在哪 | ①缺「为谁」：不相对使用范围声明的「完整整体」退化为美学判断（雕塑/作品也是完整整体）②缺「交付」：完整性必须在作者离场后仍成立——这正是 AI 时代最要命的缺口 ③缺「约束」：产品是约束下的完整 |
| 加固版 | 产品 = **对声明范围而言、交付后仍成立的**完整整体 |

## 2 工程是什么

### 2.1 经典定义（出处）

- **ECPD**（美国工程职业发展委员会，ABET 前身）对 engineering 的经典定义（大意）：**创造性地应用科学原理**，设计或开发结构、机器、装置或制造过程；**充分认识其设计**、并**预测其在特定运行条件下的行为**——全部以「预期功能、运行的经济性、以及对生命财产的安全」为准绳。信心级：转述可靠（两个独立来源给出同一定义）。
  要点：**「经济性」与「安全责任」写在工程的定义里**——约束不是工程的外部条件，是工程的构成要件；「预测其行为」= 可预测、可计算是工程的内在要求。
- **西蒙（Herbert A. Simon）《人工科学》**：「Everyone designs who devises courses of action aimed at changing existing situations into preferred ones」（凡是为把现存状况改变为更合意状况而设计行动方案的人，都在做设计）；「自然科学关心事物是什么样，设计关心事物应该是什么样」。出处：The Sciences of the Artificial，MIT Press（1996 第三版）。信心级：转述可靠（措辞与出处经检索核证）。
  要点：工程=设计=在约束下把现状改造为更合意状态——目标是外生的，约束是强制的。
- **IEEE Std 610.12《软件工程术语标准》（1990）**：软件工程 = 把**系统化、规范化、可量化**的方法应用于软件的开发、运行与维护。信心级：转述可靠（标准谱系经核证；措辞为通行标准表述）。
  要点：**「可量化」是工程的入场券**——当年给「软件」补工程资格，补的正是这一条。

### 2.2 工程三判据（核心推论二）

- **可判**：对错有机器可查、或证据锚定的判据（不是「我觉得对」）。
- **可复**：同输入同结果；有可重跑的命令与真实退出码（不是「我跑过了」）。
- **可继**：换人、换会话能接手；假设与理由随工件走（不是「作者在场才行」）。

三条全中=工程性成立；缺一条即「表演性工程」。这三条与本项目工作流的 GATE / 证据 / 账本三件一一对应——**工作流做的事，本质是把这三条判据施加在 Agent 自己的行为上**。

### 2.3 工程与手艺的分野

一次成功 ≠ 工程。桥梁：塌过一次的不算，能按预测载荷站一百年的才是。软件：在作者机器上跑通是 demo，跨环境/跨会话/跨人员持续成立才是工程。**工程 = 把一次性成功，变成可复现、可复算、可继承的持续成立。**

### 2.4 对用户定义的裁决（工程）

| | 内容 |
|---|---|
| 用户定义 | 工程是一个稳定性结构 |
| 抓住的真属性 | **稳定**——工程的核心产物确实是「持续成立」 |
| 偏在哪 | ①稳定 ≠ 不变：刚性稳定是脆的；工程稳定 = **受控变化的能力**（可版本化、可回滚、可渐进）②「结构」不是第一性：工程的第一性是**闭环**（约束→设计→验证→留证→维护），结构是闭环的产物；没有验证与留证的「稳定结构」只是审美 |
| 加固版 | 工程 = **以可复算证据支撑的、受控演化的**稳定性结构 |

## 3 产品工程是什么

### 3.1 行业既有用法（2025-2026 核证）

- **硬件/制造义（传统）**：product engineering = 把产品从概念带过设计、制造、上市的组织职能；product engineer 在半导体/机械行业是常设职位（PTC 产品页、MBA 智库「产品工程师」条目）。
- **软件角色义（近年主流）**：product engineer = 同时承担产品判断与技术实现的工程师——「对结果负责、而不是对工单负责」「一个人闭合了从问题到代码的整个回路」。PostHog、beon.tech、wavect 等 2025-2026 来源密集；PostHog 数据：产品工程师检索量 2021 年以来 +89%。「**产品死在交接处**」是这个角色存在的直接理由——规格漏掉的那个细节，只有同时握着两端的人才抓得住。
- **组织/学科义**：product engineering = 把软件当「产品」而非「项目」来建的实践——从想法到生产、并对结果负责（IBM Think、Monterail 等 2026 来源）。

### 3.2 结构性缺口：两个判据之间的无人区（核心推论三）

- 产品的默认判据是**正向完备**：「该有的都得有」。
- 工程的默认判据是**负向无错**：「已做的都不出错」。
- 两者错位：工程能验证「存在的东西对不对」，验证不了「不存在的东西该不该存在」。
- **缺失逻辑恰好落在两者之间的无人区**（对照 §1.3 三级阶梯：bug 归工程；逻辑错需规格；缺失需完备的规格）。
- 所以「产品工程」若要成立为一个工程学科，它必须回答的独有问题只有一个：**如何让「完整性」可判定。**

### 3.3 产品工程（本项目义）

**产品工程 = 把「完整性」翻译成「可判定性」的工程。**

- 它产出的工件 = **契约**：范围声明（做什么/不做什么）+ 状态空间（态与转换的封闭枚举）+ 失败与恢复路径 + 证据 + 裁决记录。
- 它的核心动作 = **翻译**：把用户要的「完整」翻译成机器可检查的「闭合」。
- 它的成功判据 = **缺失可检出**：当一条逻辑缺失时，机器或流程能在实现前/交付时把它标红。
- 它不生产的：审美与手法（设计层的活）、纪律与流程（工作流层的活）。分工一句话——产品工程管「**什么叫做对**」，工作流管「**怎么做到、怎么证到**」。
- 形式化边界（与既有三方讨论的「硬层/软层」对齐）：**硬层机器可验**（态/转换/权限/恢复/证据），**软层可追溯**（意图/权衡/理由）——不追求全链 JSON 化，否则「正确但昂贵」会杀死采用意愿。
- **补记（2026-09-23 用户定稿）**：产品工程的第一性问题不止「这个功能怎么完整」，还有更上游的**产品对象层**——这个页面为什么存在（Purpose）/职责是什么（Responsibility）/有哪些能力（Capability）/哪个最重要（Priority）/能力是否完整（Completeness）/能否被系统管理运行（Operability）；然后才进交互、状态、实现、验证。**产品工程 ≠ 产品创新**：创新属产品决策侧（该创造什么）；产品工程管「既然决定做，它具体应该是什么」——核心敌人是「产品已决定，但 AI 把它做歪了」。（细则：本体 `references/product-object.md`；四处偏移命名见 direction §十二。）

### 3.5 对用户定义的裁决（产品工程）

| | 内容 |
|---|---|
| 用户定义 | 产品工程是一个完整整体稳定的结构 |
| 抓住的真属性 | 三句里最接近的一句——「完整」（产品侧高位约束）与「稳定」（工程侧高位约束）都抓住了 |
| 偏在哪 | ①描述的是**结果**，缺**动作**：完整与稳定不会自动合体，中间缺「把完整性翻译成可判定性」这道工序 ②两个形容词各自还缺限定词（完整=对声明范围而言；稳定=受控演化）③缺分工：它管「什么叫做对」，不管审美与纪律 |
| 加固版 | 产品工程 = **把「完整整体」的完整性，翻译为「可验证、可复算、可继承」的契约工序**——让完整性第一次拥有工程级的证据强度 |

## 4 AI 时代的这一问（用户观察的工程化）

### 4.1 生成成本 vs 验证成本

- AI 把**生成边际成本**压向零：从 0 到 1 把东西做出来，越来越便宜。
- 但验证成本、完备成本、维护成本不降反升：**生成量越大，待验证面越大**。
- 稀缺性因此迁移：从「能做」迁移到「能证明做对」。本项目既有判断与此同源——AI 把组件与样式压成通缩品，溢价全部落在旅程完整性上（direction.md:16）。

### 4.2 三个失效模式 → 三个判据缺口

| 用户原话 | 工程化归因 | 缺的判据 |
|---|---|---|
| 「做完剩下的呢？」 | 交付后失效 | 去作者化后仍成立的**继承判据** |
| 「真实的用户链路真的如他所想吗？他所想的一定完整吗？」 | 模型按它想到的路径生成；它想不到的部分不进入它的生成空间，也不进入它的自检（推论，待验） | 完备性**生成判据**（六问/状态空间） |
| 「代码没 bug 但逻辑错」「只走当前最优解，不是维护的最优解」 | 局部最优；即时成本 ≠ 长期成本 | **长期成本定价**（让复用/验证成为最省力路径，direction.md:8、:10） |
| 「缺失的逻辑最可怕，你很难意识到」 | 缺失不产生信号（§1.3） | 缺失**可检出判据**（双向追溯 + 闭合检查） |

### 4.3 可证伪形式（承接既有讨论）

若本理论成立，则同一产品任务 A/B（装/不装契约层）应出现：高风险任务 **defect_escape 显著下降**（遗漏的交互/状态缺陷减少），而低风险任务**成本几乎不变**。指标四类：defect_escape / rework / coverage / cost（token·时间·steps）。反向证据：全部任务成本 +30~50% 而质量只小幅改善 = 「正确但昂贵」，理论不成立。**先跑一条高风险最小闭环（删除/恢复/权限/异步），不跑普通 CRUD。**

## 5 被否候选（定义层排除项）

| 候选 | 被否理由 |
|---|---|
| 产品 = 功能集合 | 功能是承诺的表皮；产品=承诺的集合，兑现发生在交付之后（direction.md:12） |
| 工程 = 流程/规范 | 流程是手段；工程的本体是判据与证据（§2.2） |
| 产品工程 = PM × 工程的角色并集 | 那是「谁来做」；产品工程是「什么叫做对」——角色可以合并，判据不可省略 |
| 产品工程 = 完整整体稳定的结构 | 结果描述，缺动作；且「完整」与「稳定」不会自动合体（§3.5） |

## 6 边界与假设

- 本文是**定义层结论**，不新增机制；机制层的下一步仍是「一条高风险链路最小闭环」（§4.3）。
- 「模型想不到的部分不进入其生成空间」为**推论**（标记待验），可由 A/B 的 defect_escape 维度间接检验。
- 经典定义均为二级来源核证（未逐字核对原书/原标准），信心级已逐条标注。
- 本文不改变 SKILL.md 定位段；三定义是否升格进本体 = 待用户裁决（§8）。
