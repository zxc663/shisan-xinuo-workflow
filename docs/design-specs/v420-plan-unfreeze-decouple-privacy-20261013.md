## 3. 候选方案（四种）与选优

### 3.1 方案甲 · 文本修补批（最小增量）

解冻=改冻结条款三处落点；解耦=人工清洗项目专名条目加文字说明；教训生命周期=新增 1-2 条细则；隐私门=verify 加正则；反论证=人工审一轮。

- 优点：改动最小，一天级。
- 缺点：**全部约束停在散文层**，verify/facts 无从机检（违 I3）；解耦不彻底；教训处置仍靠人记。复制 A 项目「提示词层约束、宿主无判据」的已批判错误。**不满足 R7「治根因」**。

### 3.2 方案乙 · 双库物理拆分

details.md 拆成「条款库」+「教训库」两个文件；教训带域/态字段与状态机；privacy_gate.py 独立脚本；反论证字段化。

- 优点：结构性解耦最彻底；教训账物理独立后上限逻辑天然分离。
- 缺点：**动单源与检索底座**——facts_sync 正则族、detail_lookup 2-gram 检索、verify F/G 项、deploy_injection details_count 全部重适配；「注入核心自包含/禁悬空跨文件指针」纪律受压；编号空间与引用纪律（`details #NNN`）要么分裂要么维持双文件单空间（实现别扭）。风险与工作量最大，换来的边际收益（物理分离 vs 标注分离）不成立。

### 3.3 方案丙 · 标注层双账本（同文件双账）★推荐主干

文件结构与编号空间**不动**；条目内增加机器可判元数据；405 零和改为**双账本**：

- **条款账**（工作流行为规则）：保持零和 405 上限，新增须合并/替换——I1 防膨胀立场不变。
- **教训账**（`[域:…]` 标注的踩坑教训）：**解冻单列计数**，不占 405，靠生命周期代谢（§4.2）自我平衡。

元数据三字段（全部可被 facts/verify 机检）：

```
[域:通用]            —— 跨平台可复现（判据：成因在 Agent/工程共性层）
[域:平台=<名>]       —— 成因绑定特定平台机制（如 DSH 信封包裹、Mimosa 插件拦截）
[域:环境]            —— 成因绑定作者本机软硬件/私有配置（泛用检索默认排除）
[态:active | fixed | retired]   —— 生命周期状态（§4.2 状态机）
```

配套：facts_sync 双计数（n=条款 / l=教训）+ 字段存在性校验；detail_lookup 加 `--domain 通用` 过滤；privacy_gate.py 独立脚本接 verify 新 K 项；反论证审计批产物落裁决表（不膨胀正文）。

- 优点：改动面最小且门禁兼容（I2）；双账本精准回应解冻（R1）同时保住防膨胀（I1）；域字段直接支撑平台特异性判定（R4）与泛用检索（R3）；编号空间、引用纪律、检索体验零破坏。
- 缺点：教训与条款仍同文件混排（读者靠标签区分）——但这是现有「[分类]」标签的既有形态的扩展，不是新问题。

### 3.4 方案丁 · 三域物理分流

在丙的基础上再进一步：`[域:环境]` 教训**物理移出分发面**（进 memory 归档/gitignore），`[域:平台=*]` 下沉各平台适配文件。

- 优点：分发面最干净，泛用性最大化。
- 缺点：跨域教训归属两难；平台适配文件的加载触发要重做；检索分裂（一次查不全）。**作为丙完成后的可选深化批保留，不作为主干**——先标注后分流，分流决策等普查数据（有多少 [域:环境] 条目）出来再拍。

## 4. 选定方案细化（七子件）

### 4.1 解冻条款改造（R1）

- 冻结条款从「405 零和」改写为双账本表述：**条款账零和不变；教训账解冻、单列计数、靠生命周期代谢**。
- 落点四处：`docs/transformation-plan-20261010.md` §六追加 2026-10-13 解冻决议（保留原文，只追加不改史）、`AGENTS.md` 维护纪律节改写、`README.md` 局限节刷新、agent-log 偏好段刷新（对齐原 R1.2 三处落点+计划档本体）。
- facts_sync：COUNT 拆双命名组 `(?P<n>…)` 条款 / `(?P<l>…)` 教训；全链 CARRIERS 承载点按 R1.3 先例一次联动（README/AGENTS/project-info/项目信息/CHANGELOG/三包 SKILL）。

### 4.2 教训生命周期协议（R3+R4+R5，本方案核心新机制）

**状态机**：

```
active ──(修复判定过)──► fixed ──(普查批裁决)──► 三出口
  ▲                        │                     ① retired（删除，编号入 retiredNums 不复用）
  │                        │                     ② 留库标版本上限（fixed 态本身=老版本用户仍有效的警告）
  └──────(复发)────────────┘                     ③ 合并上位（沉淀出通用原则→并入条款账，本条 retired+回指）
```

- **修复判定判据**（高举证责任，对齐「负向结论更严格」红线）：真实调用链复现尝试 ≥2 次（快/慢或新旧形态两种负载）均无法复现 **+** 对照组阳性（同环境已知坑仍可复现，证明是「上游修了」而非「我测错了」）**+** 平台版本锚定。三要件缺一 = 降「未定论」，不动状态。
- **复活机制**（I12）：retired 症状再现 → **新编号立条 + 回指退役编号**（retiredNums 不可变，机检友好），复发链记档，命中计数重开。
- **域判据写死**（R4 的答案）：专名≠环境——**判据=教训的因果是否依赖平台/环境特有机制**。提到 Next.js 的前端教训若因果在共性层（如构建缓存），仍标 `[域:通用]`。这样「博客 15 行」里大部分可能仍是通用教训，普查时逐条裁。
- 机检：facts 校验每条教训条目带域+态字段（渐进：先 warn 两个版本，后硬门）；detail_lookup `--domain 通用` 过滤=泛用场景检索默认排除平台/环境特定项。

### 4.3 域+态普查批（存量审计，R2/R3/R4 的存量面）

- 存量 405 条逐条三裁决：**域**（通用/平台/环境）+ **态**（active/fixed）+ **反论证**（§4.7 三问）。
- 分三批：批 A=项目专名机筛命中（~50 条：博客/Prisma/frp/Next.js 等 grep 起点人工确认）；批 B=按 33 类分摊全量（每批 1-3 类推进）；批 C=收口+facts 双账切换+残余裁决。
- 专名普查产出即为丁方案（分流）的决策数据：`[域:环境]` 条目数量与清单。

### 4.4 开源隐私门 `privacy_gate.py`（R6，吸收乙的独立脚本形态）

- **四层扫描面**（覆盖 I4 实测缺口）：
  1. 工作区 tracked 文本：扩展 D 项词表——QQ 邮箱正则 `\d{5,11}@qq\.com`、真名、家目录、机密目录路径（现 D 项已有后三者，补身份维度）；
  2. **git 全历史**：`git log --all` 的 author/committer 身份 + commit message 文本（首跑必红：528 命中——所以「门建成」与「存量清洗」拆成两个决策）；
  3. **发行物元数据**：package.json `author`/`maintainers` 字段（在 dist $roots 内，实测缺口）；npm/Gitee 渠道元数据核对清单；
  4. **二进制图片**：机器不全查、**清单化人工过窗**——发行前人工翻 png/截图（对齐 A ⑫「扫描器盲区人工过」）；build-dist $roots 现状不含根 png（实测安全），加断言防未来扩张（I11）。
- **判据形态**（对齐 A ⑫ 可验收标准）：block 级命中 0 + 内部产物未被 git 跟踪 + 发现真凭据时「先吊销再清理」顺序写入流程文档。禁止只写「注意隐私」。
- **统一占位符**：`<user>` / `<EMAIL_REDACTED>` / `%USERPROFILE%` / `<REPO>`（抄 A，不自创）。
- **接入**：verify-release 新 **K 项**（结构校验可 `--skip-privacy`，发行跑全量）+ RELEASE-CHECKLIST 发行前置步骤；`--selftest` 带伪造命中样本（对齐反向变异传统）。
- **存量清洗路径**（L3 破坏性，单列待拍板，不在本批施工）：按敏感度分级（I13）——QQ 邮箱 filter-repo 重写（hash 全变、双远端 force push、已发行物如实声明不可撤回）vs 只立门管增量+SECURITY.md 如实声明。

### 4.5 时间戳规范扩展（R6a）

- 现行秒级标准不动（I8），扩展**强制场景清单**：①决策记录（agent-log 决策行）；②**决策性代码注释**——含取舍/为什么不用方案 B/临时 workaround 的注释，形态 `// #决策 2026-10-13 HH:mm <取舍内容>`；③教训条目立条日期+修复验证日期；④反论证裁决日期。
- **边界**（张力处理）：普通解释性注释不强制——代码可读性优先，对齐注释纪律「只写规则本身+≤1 句为什么」；时间戳的目的是可追溯，「决策性」是判定线，不是所有注释。

### 4.6 代写言论禁令（R6b）

- **定义**：代为现象言论 = 以用户名义/口吻写下的、无用户原话锚的表述。
- **判据三条**：
  1. **默认非归因形态**：决策记录写「决定 X｜依据 Y｜影响 Z」（RE 形态已有，正好是现成载体），不写「用户拍板了 X」；仅在归因本身是判据关键时（如「作者显式批准破坏性操作」）才引用原话（引号+日期轮次锚）——这就是「只写决策」；
  2. 交付物正文（skill/）出现「用户拍板/用户裁定/用户要求/用户令」类词 = 违规（正文本就禁史料，扩 verify 净化词表即机检）；
  3. 人工回填类结论必须标执行人+原始输出，禁 agent 代填代推（对齐 A 的 D-22，现有「不假实现」红线的显式化）。
- **I5 历史豁免**：平台记忆/agent-log 既有「用户裁定」条目是有原话支撑的史料，不回溯；新记录执行新规。
- 落点：注入核心红线区加一句（须等量压缩，压缩候选预列：「自检彩蛋」段可瘦身）、agent-log 模板教训条目「证据=用户原话」字段旁加反向禁令、verify 净化词表扩展。

### 4.7 反向论证机制（R2+R6c）

- **三反事实问题**（每条机制/观点/表述）：①必要性——删掉这条，最坏真实后果是什么（有事故判例引判例，无判例标「预防性」）；②表述鲁棒性——这句话会被怎么误读/滥用（给反向样例）；③最优性——有无更短/更通用/更少副作用的等价表述。
- **分层载体**（I6 防膨胀）：
  - 机制层（judge/gate/门禁设计）：审计裁决表落 `docs/evidence/` 或 EVIDENCE 附件，不入正文；
  - 条款层（405 条）：三问结论只落**条目尾处置注记**（保留/改写/退役/合并），论证细节在裁决表——正文零膨胀；
  - 表述层：v4.1.0 表述八维 45 件全审已有先例，本次并入普查批一起跑。
- **时机**：存量=普查批（§4.3）三裁决合一；增量=新条目/晋升时 `*来源/晋升*` 字段旁加一行反论证结论（新条目量少可承受）。
- **机检面**：普查批完成后「405 条全部有处置注记」进 facts 断言（渐进同 §4.2）；防走过场=审计表抽检（facts 随机抽 N 条人工核非模板套话——语义质量诚实标注为不可全机检）。
