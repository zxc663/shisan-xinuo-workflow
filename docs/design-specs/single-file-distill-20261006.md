## 1 目标与定位

- **目标**：把主体系 v3.4.0 蒸馏成一个自含单文件 skill，供**自己跨平台携带**（ZCode / Codex / Claude Code / Trae / Cursor / Windsurf / WorkBuddy），装载即生效。
- **定位**：**衍生物，不是第二真源**——纪律语义以主体系为准；文件头声明基线与"不自动同步"。
- **两条设计原则**：
  1. **纪律不变形**：三级跑道、L3 六项、判级、必问底线、红线、记忆留档、错误必查 TOP 等**核心纪律保留原名原义**；文件层面只做删减 + 合并 + 指路。
  2. **验证机关按新平衡点精简**（用户追加口径）：保留「**可复跑**」层（最便宜的客观性），砍掉「**可审计**」硬化层（为"被外部审计"设计的制度化）——详见 §4。这是本版相对主体系**唯一有意的"变形"处**。
- **与前七项决策相容**：细则不进正文；体积不设硬限（砍验证机关后天然更收敛）；仓内伴生包；不建装载脚本；README:30 并入本批修。

## 4 可验证性 ↔ Token 的新平衡点（本次核心设计 · 用户追加口径）

**一句话**：保留「**可复跑**」层——一条真命令 + 真退出码 + 改动文件（最便宜的客观性）；砍掉「**可审计**」层——计数 / 验证层级 / 自报字段 / 外部抽检 / 判降级（为"被别人审计"设计的制度化）。省下的是**审计语义**的花费，不是**真实性**的花费。

> 口径说明：用户要"保留机制与核心纪律"——按**行为面**保留（判级/必问/门禁概念/证据概念/记忆）；"精简可验证工件"——按**实现面**精简（脚本/hooks/台账/计数/自报字段）。

### 4.1 逐项裁决表（主体系验证机关 → 单文件版）

| 验证机关 | 单文件版 | 说明 |
|---|---|---|
| 复述 + 状态行（可 grep 校验） | ✅ 原样保留 | 每轮 ~20 token，机制性价比最高 |
| GATE 概念（收尾证据行） | ✅ 保留 · 分级瘦身 | 见 §4.2 |
| ├ cmd + exit（真命令 + 真退出码） | ✅ 保留 | 「可复跑」核心 = 可验证性的最便宜载体 |
| ├ files / errpath | ✅ 保留（有才写） | files=改动清单；errpath 仅错误时一行 |
| ├ refs（细则引用 grep 计数） | ✂ 砍 | 单文件无细则库，计数无对象 |
| ├ ev=（验证层级 exec/cover/invariant/indep） | ✂ 砍 | 审计硬化层，判定复杂、易走形式 |
| ├ caps / effort（能力使用 / 努力证明） | ✂ 砍 | 自报字段，主要为外部抽检而设 |
| ├ lessons / exempt / stop_reason | ⚖ 简化 | lessons→可选一句；exempt=「未验证声明」保留一句；stop_reason→「卡住就停下说明」 |
| 证据三挂靠（cmd/exit/files 三锚） | ✅ 以字段形态保留 | 三锚本身留下；砍的是其配套审计机关（下一行） |
| gate_audit 外部抽检 + 虚假 GATE 判降级 | ✂ 砍 | 需要外部工具/审计方；单文件版以"写不出就别写"的自我诚实为准 |
| hooks（开局提醒 / 错误时刻推送） | ✂ 砍 | 平台配置面 + 维护面；需要时回主体系 |
| 机器门禁（发行 8 项 / 产品 9 台 / 风险扫描 / 检索端口 / 归档脚本） | ✂ 砍 | 主体系专有；单文件版以**人工自查清单文字**替代（不配脚本） |
| 判据金样本 / 探针 / 记分卡 / 台账 | ✂ 砍 | 面向"把本技能做成产品"的研发治理，个人携带不需要 |
| 会话状态面（§9 报告） | ⚖ 简化 | 省；日常以状态行即锚（一行注明「已折叠」等，可选） |
| 记忆留档（agent-log 四区） | ⚖ 简化 | 保留「状态段 + 流水一行」骨架；上限/归档/秒级时间戳等行政条款从简 |

### 4.2 新 GATE 定版（分级 = "新的度"本身）

- **L1**：`GATE: {level=L1, cmd=…, exit=…}`
- **L2-S / L2-F**：`GATE: {level=…, v=…, cmd=…, exit=…, files=…, errpath=…（无则省）}`
- 一行；不填的字段直接省略；**写不出可复跑命令就不写这条（不许编）**。
- 设计思路：把主体系既有的「GATE 分级（包级/子块）」思想延伸到单文件版——**按任务级别自适应验证强度**，这本身就是"在可验证与 token 之间找度"的机制化答案：小任务几乎零开销，大任务自动带上证据。

### 4.3 得失账（估算，非实测；口径=中文约 1.5–2 token/字符）

- 证据开销：主体系 ≈ 80–150 token/任务块（12 字段 + 计数 + 审计语义叙述）→ 单文件版 ≈ 25–50 token/块（4–6 字段）。日均 10 块的量级差约 0.5–1.5K token/日——**节省量级不大，主要收益是认知负担与依赖面的下降**（无脚本、无计数器、无审计话术）。
- **失去**：外部可抽检性（防自报作弊）、跨会话审计链、计数单源核验、判据自证。
- **换来**：轻、自包含、任意平台可装、行为机制全在场。

### 4.4 适用范围护栏

- 本平衡点**只用于单文件蒸馏版**；主体系的验证体系不动（其价值恰在治理与可审计——那是"源库 + 实证场"的定位）。
- 若将来想反向移植（主体系也瘦身），另立批次，不在本批范围。

## 8 风险与回滚点

- 风险①：**分叉**——衍生物定位 + 基线行 + 不自动同步（缓解）。
- 风险②：**被误当全量**——头注声明 + 回查指路段（缓解）。
- 风险③：**装载 ≠ 触达**（平台行为面不可外推，已有实证）——试针仅作冒烟，不做"保证"。
- 风险④：**工具链小改动误伤门禁**——施工前后各跑一遍 verify；回滚点 = 施工开始前 git 状态快照（当前工作树含未提交的 v3.4.0 收尾改动，施工第一步先清点+留回滚点）。
- 风险⑤（新平衡点特有）：砍审计层可能被"三挂靠爱好者"质疑——记录口径：这是**有意的平衡点选择**（设计档 §4 为凭），非疏漏；主体系仍是强核验选项。
- commit 通道：本仓 commit 受 Mimosa 拦截的既有裁定不变——产物可能需用户终端代提（同现有欠账流程）。
