## 三、`[域:环境]` 清单 = 空（丁方案决策数据）

**实测结论：存量 `details.md` 无任何条目因果绑定本机私有配置（用户名 / 本机路径 / 私有端口 / 私有凭据位置）。**

既有 `[环境]` 分类标签 11 条（#187 #188 #189 #224 #225 #257 #258 #259 #271 #297 #300）经复核，其内容绑定的是**平台机制**（Windows 保留端口段 / schannel / PowerShell 五坑 / Node ESM loader / xargs 缺失 / TS 版本矩阵 / pnpm overrides / WSL PATH），**不是本机私有配置**——这些坑在任何 Windows 机器上都能复现，故判 `[域:平台=…]` 而非 `[域:环境]`。

**对丁方案（物理分流）的决策含义**：分流的前提是「环境条目量大、污染分发面」，实测该集合为空 → **丁方案当前无决策数据支撑，不构成分流理由**。若未来出现真正的本机私有教训（如某代理端口号、某本机路径陷阱），按入库六步进 `lessons.md` 标 `[域:环境]`，届时再评估分流。

## 四、分拣裁决：存量零迁移

**逐条复核 49 条候选后的结论**：

条款账 405 条的正文形态统一为「**机制如何出错 → 对策**」，其中**对策本身就是行为规则**（祈使句 + 动作：必须/先/禁/一律 + 做什么）。按分拣判据拆分会出现两难：

- 若只迁「坑的描述」而把对策留条款账 → 迁出的教训账条目只记录「坑长什么样」，检索到的 agent 拿不到「该怎么做」，反而**削弱**检索价值；
- 若整体迁走（含对策）→ 条款账失去该防护点，对策离开常驻检索面，**净损失保护面**。

**实证支撑**：逐条阅读 49 条候选（#205 #207-#212 #217 #219-#222 #225 #226 #240-#244 #250 #256-#271 #297-#305 #380 #388 #392 #400-#402 #404）确认——全部为「机制 + 对策」复合形态，无纯叙事条目。**踩坑叙事实际载体在 `*来源/晋升*` 史料字段与 `memory/agent-log.md` 教训区**（如 #294「占全部工具错误 55%（186/337）」、#375「667MB 活跃会话于两轮快照间消失」均在此），不占用条目正文。

**裁决（作者确认）**：**存量零迁移**，`lessons.md` 保持 0 条为**合法初态**（非待施工半成品）。分拣判据不变，供增量条目适用——此后真实踩坑按 `flows §11` 入库六步（域判定 → 态标记 → 反论证三问 → 证据锚 → 落库 → 修复判定）进账。

**推论**：条款账活跃条数保持 405 → **全链 CARRIERS 无需联动刷新**（facts 全绿即证）。
