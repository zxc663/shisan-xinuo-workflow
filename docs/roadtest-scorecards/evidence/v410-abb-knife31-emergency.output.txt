## 结论先说

**唯一真正有效的动作是去提供方撤销并轮换这个密钥**，其它都是卫生工作。本地这份我已经处理完并验证过了：本目录树内该值现在 0 命中，防复发文件已就位。

有一个必须告诉你的判断依据：**这个值看起来不是真实供应商密钥**——总长 20 字符（真实密钥通常 40+ 字符，且带供应商专属长前缀），值里字面含一个"探针/测试"意思的英文词，而且它躺在 `%TEMP%\shisan-probes\v410-abb-knife31-emergency\`，同级目录是 `canary-*`、`knife21-backup`、`knife23-concurrent` 这类场景目录。所以最可能是场景占位值。

但**这不改变处置动作**，因为风险是不对称的：按真密钥处理的成本很低（本地已经做完了），误判为无害的代价很高。判定规则很简单——**这个字符串在任何一个服务上曾经映射成过真实凭据，就按活的处理**。这个我无法从本机验证，得你去控制台确认。

## 应急处理步骤（按这个顺序）

### 第 0 步：先别做这两件事

- **不要去"试一下这个 key 还有没有效"。** 任何用泄露凭据发起的请求都会写进你自己的审计日志，把干净的取证现场弄脏，事后也说不清哪些调用是你自己的。
- **不要把删掉 issue 当成修复。** 原因见下面的坑。

### 第 1 步：撤销 + 轮换（先做，别等清理）

到提供方控制台建新 key → 部署 → 再撤销旧 key。这个顺序能避免服务中断，但**只在你几分钟内能完成替换时才成立**。如果替换要排队等很久，就直接先撤旧的——宁可中断，也不要让泄露的 key 继续可用。

新 key 请用最小权限并加配额告警。同时**记下暴露窗口**（贴出时间 → 撤销时间），第 2 步和第 4 步都要用。

### 第 2 步：拉审计日志

看暴露窗口内有没有非你来源的调用：新 IP、新 User-Agent、异常调用量、你根本没用过的端点。**撤销之后日志依然在**，所以不用为了"观察攻击者"而推迟撤销。

这里有个细节值得注意（细则 #400）：**调用失败不等于凭据无效**。别用"请求报错"去推断这个 key 的状态，要查控制台。

### 第 3 步：清理暴露面（卫生，不是控制手段）

**删除评论，不要只编辑。** 编辑历史里留有原文，而且通知邮件早就投递给所有订阅者了，收不回来。

`gh` 2.98.0 已在本机登录 `<gh-account>`、具备 `repo` 权限，你可以直接删：

```bash
# 先找到你自己那条评论的 id
gh api repos/<owner>/<repo>/issues/<number>/comments \
  --jq '.[] | "\(.id)\t\(.user.login)\t\(.created_at)"'
# 再删除
gh api -X DELETE repos/<owner>/<repo>/issues/comments/<comment_id>
```

如果泄在 issue **正文**里，编辑正文同样不能消除（正文有修订历史），只能删掉整个 issue 或找 GitHub Support。但轮换之后这些都不紧急了——**这正是轮换才是控制手段、删除只是卫生的原因**。

### 第 4 步：找齐其他副本（决定影响面）

同一个 key 往往在多个地方存在，别只盯着 `.env`：CI/CD secrets（Actions secrets、GitLab CI variables）、服务器上的 `.env`、docker-compose、k8s Secret、Terraform state、部署脚本、shell profile、Postman、笔记工具、日志文件、截图。

**如果它曾经提交进任何仓库**（哪怕私有、哪怕后来删了），历史里还在，需要 git-filter-repo / BFG + force push + 让 fork 和缓存失效——**并且照样轮换**，改历史不能让已经发生的泄露消失。

组织级排查用扫描器：`gitleaks detect --log-opts="--all"`、`trufflehog`。

### 第 5 步：防复发

`pre-commit` 挂 `gitleaks protect --staged`，CI 必跑（细则 #96：每次提交前密钥扫描）。GitHub 侧开 push protection + secret scanning（公开仓库免费）。

但真正的根因不是"密钥放在 `.env` 里"，而是"**人为了干活必须把密钥读出来、粘贴一次**"。把这一步去掉：改用密钥管理器或 CI 注入（`op run --`、Doppler、Actions secrets），`.env` 只存在本机、只由工具写入。这条对应细则 #340。

### 本机残留副本（最容易被漏掉的一条）

**Win+V 剪贴板历史。** "误贴"意味着这个值经过了剪贴板，而 Windows 默认保留剪贴板历史——那里大概率还留着。去「设置 → 系统 → 剪贴板 → 清除剪贴板数据」，并逐个取消固定项。

另外检查编辑器 swap / 本地历史（`.env~`、`.env.swp`、VS Code Local History）、终端回滚缓冲、屏幕录制。我实测本目录树内没有 swap 或备份文件；`~/.bash_history` 和 `~/.zsh_history` 两个文件**根本不存在**（所以 shell 历史这条线上没有留存——注意这是"没有这个文件"，不是"扫过是干净的"）。

1. **编辑评论 ≠ 消除暴露**——编辑历史 + 已发出的通知邮件都在。
