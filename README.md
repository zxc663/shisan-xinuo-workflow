# Shisan Xinuo Agent Workflow（十三希诺 · 纪律元工作流）

> **v4.0.0** · MIT · 单人维护 · [GitHub 源库](https://github.com/zxc663/shisan-xinuo-workflow)

**一句话定位**：把「工程纪律」从提示词升级成**机制**的元工作流——三级跑道分流、L3 封闭清单停点、可复跑 `GATE` 证据块、跳过必声明。它不承诺更好的代码，它承诺**更少的事故**。

---

## 作者的话

> **「工程化的确定性和稳定性，才是让 AI Agent 从玩具落到实地的真正要点。」**

确定性，是同一套纪律换一个会话、换一个模型、换一个平台仍然复现——所以这里的每条规则都带**触达端口**（注入锚点 / 错误时刻推送 / 预读 TOP），而不是靠"希望模型记得住"；该问的停下来问，该跑的真跑一遍。

稳定性，是不因遗忘、压缩、换人而失效——所以这里的结论必须**可复算**：`GATE` 带真实命令与退出码，判据有版本与金样本回归，高危动作被 L3 停点拦在发生之前。过程对得起复核，结论对得起复算；**做不到的，这里不写进承诺**。

## 这是什么，不是什么

### 它是什么

一个 **纪律元工作流（discipline meta-workflow）**：只管 Agent「怎么做」，不管「做什么」。它把工程纪律做成四样可以真正执行的东西——**流程结构**、**可跑门禁**、**可复算证据**、**停点与记忆**。

### 它跟 AGENTS.md / CLAUDE.md 的分别

- **AGENTS.md / CLAUDE.md 是「载体」**——声明式配置，告诉 Agent「这个项目怎么构建、什么风格、哪些红线」。
- **本工作流是「引擎」**——命令式流程，规定 Agent「任务怎么分级、什么时候停下来问、做完怎么留下可重跑的证明」。
- 它**往这些载体里写东西**：平台适配检测到 Codex / Claude Code / Trae / WorkBuddy / ZCode，就把浓缩纪律写进对应的 `AGENTS.md` / `CLAUDE.md` / 平台规则文件，先备份、合并不覆盖，再回指本 Skill 取详细规则。

一句话：AGENTS.md 是法律条文，本工作流是**律师 + 执法记录仪 + 卷宗归档流程**。一个诚实的边界：它写进去的东西本质仍是提示词，只是外面套了一层能真跑的脚本与门禁——它没有跳出提示词范畴，而是把提示词范畴用到了接近极限。

### 它不是什么

- **不是代码质量工具**。质量由评审与测试负责，本工作流不碰。
- **不是零事故保证**。它降低的是「根本不该发生的动作」（删库、泄密、误发布、失守迁移）的发生率，不是缺陷率。
- **不是企业级治理平台**。没有身份认证、策略引擎、平台级审计，只是提示词级的一层纪律。

## 真正有分别的地方

同类项目大多在做「流程强化」或「全家桶打包」，本项目做的是**把纪律变成可证伪、可回归、可追溯的实证对象**。七样机制里，前四样常见，后三样罕见：

1. **三级跑道**（L1 快速通道 / L2-S 短工作流 / L2-F 完整 9 步）——按任务风险选深度，不为所有任务套全套流程。
2. **L3 封闭清单**——仅 6 项（密钥/权限｜数据删除｜迁移｜对外发布｜架构选型｜超预算破坏性操作），清单外一律不是 L3、不得自行扩展；命中**先问再做**。清单外高危域（CI/CD·DNS·IAM·计费·feature flag·webhook·限流·OAuth 回调·生产配置写·IaC 落盘·基础设施 reload）另有 `risk_scan.py` 机检兜底。
3. **GATE 12 字段证据块**——每个任务块末尾一行可重跑证据（`level/v/cmd/exit/files/refs/errpath/lessons/exempt/caps/effort/stop_reason` + v3.4.0 起 `ev=` 验证层级 exec/cover/invariant/indep）。把「我做完了」强制变成「这是命令、这是退出码、你重跑一遍」。
4. **跳过必声明**——任何规则/步骤被跳过，必须复述跳过项、留依据、向用户一行提醒。「跳过+声明」合法，**静默跳过违规**。
5. **判据版本化（j1.0→j2.5）+ 金样本回归 23/23**——行为面探针的判据是代码（`probe_runner.py`），改判据必过 `--judge-selftest` 并在 `JUDGELOG.md` 留一行变更记录。**判据即代码**，这是同类项目普遍没有的。
6. **反向变异自测 / 内容哈希验收 / 叙述对账 / 反作弊**——门禁自带负向样例；五平台注入副本做内容哈希验收（版本串一致≠内容一致）；`facts_sync.py` 让全部数字单源可断言；`gate_audit.py` 对虚假 GATE 降级。
7. **with/without 双仓对照 + 负面结论更严**——判"不复现/不存在"需判据逐字对齐 + 真实调用链，否则降"未定论"。

## 与同类项目的分别

2026 年 9 月的对标调研（`docs/comparison-v290-analysis-20260916.md`，11 个项目、6 维矩阵）把同类项目分成四类，本项目与它们都不同：

| 类别 | 代表 | 它们做什么 | 本项目的分别 |
| --- | --- | --- | --- |
| **A · 流程强化** | `obra/superpowers`（≈297k★） | 引导协议常驻化、子代理流水线、会话诊断技能 | 机制可借（每任务审查、Ruling 账本、技能写作 TDD），但本项目重心不在「流程更顺」，而在「结论可复算、事故先停」 |
| **B · 规则承载全家桶** | ECC + Toolkit 类 | 把大量规则/工具打包 | 本项目不做全家桶，做的是**分层渐进披露**——常驻 ≤6000 字符，细则按症状索引按需加载 |
| **C · 多智能体编排** | MetaGPT、ChatDev | 角色编排、流水线协作 | 本项目是**单人单 Agent 的纪律层**，不编排多智能体 |
| **D · 企业治理平台** | Microsoft 类 | 身份认证、策略引擎、平台审计 | 本项目无这些；它是提示词级的一层纪律，换来的是可测试、可复算 |

一句话分界：**主张说小、证据说满**——superpowers 的 README 通篇不提 token/成本，本项目把「治理有代价、代价有界且可审计」写进头条；superpowers 把评测放独立仓，本项目把探针与 scorecard **随仓**并判据版本化。对标结论记录在 `docs/design-specs/benchmark-superpowers-20260929.md`（借鉴点/现状/移植成本/验证法四列）。

## 四包体系

四包独立可装、组合使用（`pwsh scripts/install-skill.ps1 -Family` 一次装齐）：

| 包 | 定位 |
| --- | --- |
| `shisan-xinuo-workflow` | **核心**：三级跑道 / 判级 / 必问与红线 / `GATE` / 状态锚定 / 承载与留档 / 五平台注入 |
| `shisan-xinuo-flows` | **流程包**：9 类任务工作流分册（新功能/Bug/重构/迁移/发布/前端/运维/文档/调研） |
| `shisan-xinuo-roles` | **角色包**：8 个审查/执行角色（critic/risk-reviewer/security-auditor/debugger/contract/test/frontend/perf） |
| `shisan-xinuo-product` | **产品工程包**（独立版本线 v0.2.7，设计源与实证在独立仓 [product-engineering-skill](https://github.com/zxc663/product-engineering-skill)） |

### 产品工程包——它想解决的问题

产品工程包针对的是另一类失败：**「产品该有的都得有」缺了没人报**。缺失是不可观测的偏差——测试全绿不代表该有的都在。

它的核心思路，用作者原话就是这几句：

> **「3 万与 30 万的功能清单可以完全相同，差价全在旅程完整性。」** AI 把组件与样式压成通缩品，溢价全部集中在体验完整性——第一次打开知道去哪（空态有引导）、等待不焦虑（进度有预期）、出错不慌（错误有出路）、反悔有路（撤销与确认）、下次回来还认识（持久一致）。

> **「产品工程 ≠ 产品构想。」** 创新属产品决策侧（该创造什么）；产品工程管「既然决定做，它具体应该是什么」——核心敌人是「产品已决定，但 AI 把它做歪了」。

> **「实现层完备 ≠ 产品工程完备。」** 下游全绿不能补上游的缺。产品工程 = **把「完整性」翻译成「可判定性」的工程**——它的成功判据是「缺失可检出」。

落到机制上，是八样可以真跑的东西：

- **层级门（L0-L10）**：先定位「在回答哪一层的问题」，再检上游，未确认停下回补、不得越级下沉。
- **产品对象六问**：Purpose 为什么存在 / Responsibility 职责句（「X 管理」，不是「展示 X 数据」）/ Capability 能力清单 / Priority 恰好一个主功能 / Completeness 能力完整 / Operability 后台能不能管。
- **功能面盘点**：把用户在应用里会看到的**一切可见面**（含管理面/空态/错误页/加载/帮助）先枚举出来——漏盘点面 = 后续一切工序对它失效。
- **statechart C1-C7**：无死端 / 全可达 / 错误态必有恢复转换 / 引用完整性 / 契约 recovery 双向对账。
- **spec-trace 双向追溯**：正向每条功能行有元素兑现，反向每个元素回指功能行——反向断裂即发明或遗漏。
- **双底双顶**：不难用/不难看/无障碍为底线，更好用/更好看为上限。
- **8 台可重跑门禁**（registry / statechart / spec-trace / product-object / l0-l5 / frontend-lint / a11y / usage-probe），各带 `--selftest` 正反样例。

## 它能拦住什么

它拦的是「根本不该发生的动作」——这类动作不靠写得更优雅来防，只靠停点来防：

| 事故形态 | 拦截机制 |
| --- | --- |
| 密钥写进代码 / 提交 / 对话 | L3 封闭清单（密钥/权限）命中先问 + 门禁 D 项泄漏扫描 |
| 未经确认的对外发布 | L3「对外发布」停点 |
| 通配符 / 递归删库 | L3「数据删除」停点问询 |
| 无回滚点的数据 / 服务迁移 | L3「迁移」停点 + 回滚点红线 |
| 「你看着选」式笼统授权被扩大 | 只覆盖明示项，未答项仍必问 |
| 清单外高危域 | `risk_scan.py` 机检，命中至少按 L3 停点 |

## 值得读的记录：一份可复用的实证方法论

这个仓库最容易被忽略的价值，不是那 406 条规则，而是**它把「怎么验证一条纪律真的有用」这件事本身做成了可复用的工件**。下面这几份记录，任何想把规则工程做扎实的人都能直接照着学：

### 事故处置记录（踩坑复盘模板）

- **`docs/incidents/zcode-db-corruption-20260918.md`** —— 一次真实事故的完整处置与交接：全树「PAT 消毒」脚本把两个 SQLite 二进制库当文本重写，导致 ZCode 启动报 `corrupt`。记录含报错原文与日志对证、受损面实测表、根因（非法 UTF-8 字节被替换成 U+FFFD，1 字节变 3 字节，页对齐整体错位）、三条修复路线、照抄可跑的抢救命令、以及**禁止清单**（消毒必须带扩展名白名单 + 魔数校验双保险）。这是「事故→根因→预防回流」闭环的范本。

### 行为面 scorecard 时序库 + 判据版本史

- **`docs/roadtest-scorecards/README.md`** —— 103 个 jsonl / 8304 行 / 1047 探针行的**跨批次可比的时序库**，聚合器按统一口径剔废/分型/三态对比。它专门告诫「直接读原始 jsonl 会得出错结论」——68% 作废率是 provider 欠费窗的历史沉积，不是行为面结论。
- **`docs/roadtest-scorecards/JUDGELOG.md`** —— **判据即代码**的版本史（j1.0→j2.5）。记录了三次「判据滞后」假 FAIL（高质量合规形态被旧词表误判）、`effort=` 自满足被 GATE 字段名本身满足的空转问题、以及环境死亡行从「人工批注」变成「机器签名」的演进。判据改动必须 ① bump `JUDGE_VERSION` ② 过金样本回归 ③ 留变更记录。

### 逃逸分析 → 回流闭环（验证机制的真实证据）

- **`docs/field-trials/jz-01-ledger/SCORECARD.md` 等 7 张合成试金石卡（jz-01~07）+ 2 张实地轨卡（site-01/02，真实存量项目只读实测）** —— 每张合成卡拿一个「现实中等水平」的合成产物跑 8 台门禁，再做**逃逸分析**：逐条枚举夹具中真实存在、首跑没被抓到的缺陷，判定「真缺口 / 半缺口 / 边界外」，真缺口**回流成新的判据**（如 E1 空态无引导→回流 R5-W；E2 click-div 伪按钮→回流 A3b），回流后复跑必须命中。带星行的「回流前不命中、回流后命中」就是回流效力的直接证据。jz-02 卡还记录了一个回流时自己抓到的 bug（`if backend_list:` 把空清单当 falsy 跳过）。

### 反向注入（自测全 PASS ≠ 反向防御）

- **`docs/reverse-injection-gates-20260929/REPORT.md`** —— 27 例变异夹具：**漏报 15 / 误报 1**，其中 `--selftest` 全 PASS 与 15 漏报并存，直接证明「自测只盖正向样例、反向变异是盲区」。每条例给出根因（`if main_fn and …` falsy 短路、`startswith(("展示","显示"))` 只查前缀、字符串 truthy 判真等）与修复建议。
- **`docs/riskscan-measure-20260929/REPORT.md`** —— 双臂实测：召回 12/14（86%），良性臂噪声 4/6（67%）——诚实标注枚举外域（terraform/nginx reload）与噪声地板。

### 细则查重裁决 + 对标调研

- **`docs/mining-dedupe-20260929/REPORT.md`** —— 29 条候选 × 405 条 details 的查重裁决，四态判定（撞车已有 6 / 增量并入 10 / 新颖可立 10 / 非细则 3），「只查重不增条」的边界纪律。
- **`docs/design-specs/benchmark-superpowers-20260929.md`** —— 对标 obra/superpowers 的可吸收清单，每条带借鉴点/现状/移植成本/验证法四列，并明确「不抄什么」（不抄成本滤镜、不降级去抄独立 evals 仓）。

### 对外反馈

- **`docs/methodology-rule-verification.md`** —— **「怎么验证一条 agent 规则真的有用」的实证方法论（可移植版）**：三层缺口（在场/遵守/有用）、判据即代码+金样本回归、逃逸分析→回流闭环、反向变异自测、双臂对照与作者污染、环境死亡纪律、负面结论更严、以及**何时别用这套**的过重判定——每节锚定本仓证据工件，可逐条复核。
- **`docs/mimosa-feedback-pack-20260929.md`** —— 向 ZCode 插件侧提交的误标反馈包（M1-M10 实例 + 7 条最小复现件 + 7 条修复建议），回执 [zai-org/zcode-plugins#58](https://github.com/zai-org/zcode-plugins/issues/58)。它自己就是「把踩坑做成可复现证据」的示范——连「检测器误标会把工程实践推向更危险写法（为绕检而拼接 shell 字符串）」这种方向性反效果都记录在案。

## 局限与代价

- **上下文成本真实存在**：注入核心常驻 ≤6000 字符（中文约 4–6K token），细则按需 1–3K。窗口越小，收益/成本比越需要权衡。
- **提示词边界**：无论注入做多少层，终究是提示词范畴，抵不上平台级「新会话自动加载」的机制保证。
- **平台行为有方差**：无头模式注入面可能断裂；hooks 落盘受平台持久化策略影响。行为结论只认请求体/rollout 层证据。
- **维护成本**：细则与副本需要同步；改模板 ≠ 改副本。细则库实行**零和上限**（406 为当前上限，新增须合并/替换旧条）；判据冻结于 j2.5、聚合器冻结于 a1.1——维护态不加层。
- **单人维护**：505 次提交中 501 次署名作者本人、4 次为 agent 自动提交通道，无协作者、无维护者梯队。
