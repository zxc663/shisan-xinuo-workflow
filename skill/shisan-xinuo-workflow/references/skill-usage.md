# Skill 使用模块：能力发现 / 加载决策路由 / 文件级加载决策

> 任务涉及 Skill 选用、前端 / 设计类任务、本地无 Skill 时如何获取、弱模型 / 上下文受限处理时加载本文件。
> 与 `rules` #26/#28/#29/#38、`security.md` 安装校验、`platform-adaptation.md` §1/§2 交叉引用。

## 0. Skill 能力来源与发现机制（元能力）

- **Agent 能用的 Skill 能力，前提是被平台注册进「可用 Skill 清单」**——每会话注入所有可发现 Skill 的 `name + 一句话 description`（即会话上下文的 available skills 列表）。**未被注册 / 注入的 Skill，文件即使存在也无法被 Agent 触发**。
- **三层加载模型**（平台天然如此）：
  - **L0 注册清单**（name+description，平台全量注入、每会话常驻）——用于**发现与匹配决策**，不触发即不占正文。
  - **L1 主文件**（`SKILL.md`，触发后按需读取）。
  - **L2 `references/`**（按需渐进读取）。
- **触发决策链路**：任务 → 扫 L0 清单 → 读多条 description 判定命中 → Skill 工具按 name 触发 → 读 L1 → 渐进 L2。**description 质量决定匹配准度与误触发成本**（描述精炼 + 含触发词 → 命中准、成本低；反之易误判或被迫整读正文）。**触发 Skill 仅能用注册清单里的「确切 name」**——字母前缀 + 插件态用 `plugin:skill` 全名；测试 / 训练记忆里的 Skill 名一律**不准猜、不准拼**，只能用注入清单中的实名。
- **Agent（子代理）注册维度**：能否用 Skill **取决于执行体自身是否注册了 Skill 工具**，与文件是否存在于磁盘无关。纪律两条：①**委托任务是 Skill 能力范围的，先核对该子代理已注册 Skill 工具**；未注册则改用带 Skill 的 agent 类型或**留在主会话执行**，不把 Skill 依赖任务委托给无 Skill 的 agent（如 `browser_use` 这类无 Skill 工具的 agent）；②子代理**不继承**主会话平台注入副本、且**不保证**触发 Skill 加载（实证：已注册 Skill 工具 + 明确提醒「可读任何 skill」仍 0 加载）——委托时主代理**必须把最小纪律包内联进子代理 prompt**（判级 / 红线 / 证据四要件 / 错误必查 TOP / 引用形态 / GATE，见 rules #28），主会话不在子代理之外重复装载同一 Skill（省 token）。此为通用纪律，记入 `rules` #28。
- **平台差异**（承 `platform-adaptation.md` §1/§2）：Trae 经上下文注入可用清单、正文按需；Claude Code 需要 Skill 先注册到 `.claude/skills/` 才能被解析（**文件在 ≠ 能用，依赖平台解析**）；Cursor / Windsurf 等按平台机制。加载纪律须按所论证平台与「是否已注册可发现」适配。
- **注册 vs 使用分离**：创建 / 注册 / 更新 Skill 属**元能力**（规则类走 `rules.md` §38 六步流程）；本模块只管**「已注册 Skill 的使用加载纪律」**，两者不混。
- **弱模型 / 技能库过大的处理**：即便只注入 description，几十个 Skill 的 name+description 全量常驻也可能冲破弱模型上下文 → 弱模型下调小可发现清单（平台层过滤 / 只保核心）、依赖精准 description 避免误触发。
- **使用技能前先过层级门**（§9 技能基质层）：定位 → 检基石（S0 注册 / S1 纪律底 / S4 项目约定）→ 放行或回补；本节管「清单与触发」，§9 管「按层装配与协同」。

## 1. 何时用 / 何时不用 Skill

- **用**：能提升专业能力、任务属 Skill 能力范围（写作 / 分析 / 前端 / 支付 / 文档 / 数据等）。
- **不用**：**弱模型 / 上下文受限时**——Skill 全文会冲破上下文限制，改为精简加载或不用，只保留主流程核心（判级 / 红线 / 必问）；不习惯或尚未理解 Skill 使用的用户，先引导其认识 Skill 能提升大模型专业能力，但**弱模型可能不需要 Skill**——强行加载会冲破上下文，需按 §5 判定取舍。

## 2. 本地 Skill 优先，渐进式加载使用

- 有本地 / 工作区 Skill → **优先按渐进式加载使用**（先主 SKILL.md → references 按需），**不重复自研**。

## 3. 本地无 Skill 时的获取流程

1. **先问用户**（`platform-adaptation.md` 第 4 节提问降级链）二选一：是否需要寻找**权威 Skill 源**安装 / 本机是否有**其他 Skill 安装目录**可复用。
2. **权威源判定**：一手源（官方仓库 / registry / skills 生态）> 实证源（stars / 维护 / 采用）> 社区口碑；**安装必走 `security.md` 开源安装强制校验流程（1.5 节 6 步）**。
3. **本机其他目录复用**：先按能力 / 描述筛选，**确认已在平台注册可发现后再渐进式读取**，不重复引入；未注册则按平台机制登记。

## 4. 文件级加载决策（读哪些文件、何时读）← 加载单元=文件

- **默认：先主后引**——读 Skill 主文件（SKILL.md / SKILL），references 按当前步骤需要打开（文件级，打开即全文）；不预载全部引用文件，上下文预算不浪费。
- **打开 references 全文的三类情形**：
  1. **核心治理 / 工作流类**——引用具体编号或需裁决规则语义时加载对应全文（同 `rules #26`；原「无条件全读」实测 0 触发已休眠条件化）。
  2. **前端 / UI / 设计类——清单制**：设计类任务**开工时列必读 references 清单**（组件规范 / 设计 token / 可用性规则），清单内文件全读；清单落开工留档可核验——完备性由清单承载，不靠「无条件全读」命令。
  3. **用户明确要求完整读取 / 无预算限制时**——以用户显式要求为准（针对上述两类以外的普通 Skill：用户点名要读全文时不因省 token 而缩减）。
- **按文件触发的**：工具型 / 辅助型 / 按需触发型 Skill → 主文件+按需引用文件。
- **前端 / UI / 设计类 Skill 示例**（仅作类别举例的通用实名，命中即按清单制读其 SKILL.md 与清单 references）：`frontend-design` / `html-report` / `html-deck` / `shadcn` / `web-design-guidelines` / `theme-factory` / `canvas-design` / `brand-guidelines` 等。
- **装配顺序与基石检查见 §9**：本节管「读哪些文件、何时读」，§9 管「按什么顺序装、缺基石怎么办」（技能层栈 S0-S4 / 装配序列五步）。

## 5. 弱模型 / 上下文受限处理

- **判定（不做硬阈值，定性）**：模型能力弱，或上下文将耗尽 → **只加载能打动任务的最小核心**，重 Skill 拆成子任务 / 新会话执行。
- 决策留痕（reason 记入任务记录）。

## 6. Skill 描述（description）质量纪律（对 Skill 作者，兼作选用依据）

- 描述应**精炼、含明确触发词**，使 Agent 仅凭 description 即可高准度判定命中——降低误触发与整读正文的成本。
- 描述概要与实际能力**不符（夸大 / 过时）是匹配失误与上下文浪费的头号成因**；发现 Skill 说明与实现不符时诚实标注。 **体积纪律**：description 超平台截断阈（~1024 字符级）后**静默丢弃**——核心触发词写在前，总量建议 ≤500 字符。

## 7. Skill 与 MCP / 工具的关系（能力边界）

- Skill 可能携带 tools / MCP（按平台机制暴露）；触发 Skill 即解锁其工具，使用纪律与分级 / 留痕 / 成本规则一致（`rules.md` §28/§29）。
- Skill 能力缺失时按 `security.md` / 流程包（`shisan-xinuo-flows`）「能力缺失降级」降级，不阻塞。
## 8. 家族产品工程包挂接（条件式钩子——分合自适应）

家族第四包 `shisan-xinuo-product`（联通层：功能语义↔交互逻辑的可判定契约——判定表/能力地图/裁决账本/门禁脚本）与 flows/roles 同范式：**独立可装、建议同装、按需加载**。

- **检测**：Skill 工具可加载 `shisan-xinuo-product` 或技能目录存在该包 → 在场；否则未装。
- **在场 → 三缝合点生效**：①**计划时**——前端/功能设计任务把「能力地图检索位」写入计划；②**GATE 时**——涉 UI/功能交付，cmd 须含产品门禁可重跑命令（registry-gate 等），exit 吃真值；③**收尾时**——设计裁决回写其 `decision-ledger`（裁决语义账本）。
- **未装 → 跳过+声明**：三缝合点全部跳过，GATE `exempt` 字段声明「product 包未装」——跳过+声明合法，静默违规照罚（与接续豁免同规）。
- **单一权威**：本钩子只做条件挂接与路由，不复制 product 包任何内容；钩子与包可各自独立演进（分合都可用）。
- **裁决冲突优先序**：底线门禁 > 流程纪律 > 品味裁决。
- **通用缝合见 §9**：本节三缝合点是 product 包专用挂接；通用化的「缝合契约六字段 / 层级门 / 归因」在 §9——本节只引用，不重复定义。

## 9. 技能基质层（Skill Substrate · S0-S4 层栈 + 层级门 + 缝合契约）

> 回答「skill 使用 basic skill（基础纪律技能）之后要用到的思想」：基础技能=基质（S1），其它技能在其之上装配 / 协同。本层只做「定位 / 门 / 契约 / 归因」——三层加载模型（§0）、渐进读取分类（§4）、子代理注册纪律（§0）、家族三缝合点（§8）保持原节单一源，本层只引用不复制。
> 命名纪律：裸 `S+数字`=技能层栈（本节）；不与产品工程包 `L0-L10`（产品层级）、`档0-档3`（风险深度）、`判级 L1/L2-S/L2-F`（工作流）混用。
> 来源：产品工程「层栈 / 层级门 / 契约」思想的同构移植（设计档 docs/design-specs/skill-substrate-20261006.md）。

### 9.1 技能层栈 S0-S4（装配坐标）

| 层 | 名称 | 内容 | 本仓对应 |
|---|---|---|---|
| S0 | 平台注册层 | 「能不能被发现」：可用技能注册清单 / 注入面 | 平台机制（§0） |
| S1 | 基础纪律层（基质） | 「怎么做事的底线」 | 核心包 / 单文件版（basic skill） |
| S2 | 家族治理层 | 流程分节 / 审查角色 / 产品工程能力 | flows / roles / product |
| S3 | 专业人员层 | 把活干得更专业的外来技能 | ponytail、ui-ux-pro-max、docx/pptx… |
| S4 | 项目约定层 | 项目现实（规则文件 / memory / 既有文档）——横向最高裁量（用户现场指令在其上） | 项目 AGENTS.md / memory |

装配语义：下层是上层的地基（技能叠在纪律上）；S4 是项目现实，覆盖之上；冲突裁决用既有仲裁序（单一源=注入核心）。

### 9.2 层级门（三段式：定位 → 检基石 → 放行 / 回补）

1. **定位**：先写出来「这是哪层的问题 / 该用哪层的技能」（如「这是 S3 视觉打磨任务」）。
2. **检基石**（三项必查）：①该技能在 S0 注册清单里吗（未注册=文件存在也触发不了）；②S1 基础纪律在场吗（产出将由谁的门收口）；③S4 项目约定读了吗（项目优先）。
3. **放行 / 回补**：三项齐 → 放行；缺 → 停下回补（先装基础技能 / 先读项目规则）——**禁越级下沉**。

铁律：**技能本体完整 ≠ 基质完整**——技能再漂亮，纪律底缺位就是缺基石。

触发拦截（检查点，细则引用既有节）：

| 触发信号 | 必查 | 缺项动作 |
|---|---|---|
| 直接上领域 / 专业技能的活（未装基础技能） | S1 | 先装基础技能（单文件或核心包），再谈技能 |
| 加载 / 使用外来技能 | S0+S1 | 未注册→先注册；纪律不在场→跳过 + 声明 |
| 子代理跑带技能的活 | 子代理注册面（§0） | 未注册→留主会话或换 agent；最小纪律包内联（rules #28） |
| 多技能说法冲突 | 仲裁序 | 裁决 + 留痕；同因两次升格常设 |
| 技能产出要交付 | 出口交门 | 进基础技能的 GATE / 承载 / 交付五查 |

### 9.3 装配序列（基础技能装载之后：五步）

1. **平台与注册面**（S0）：确认目标平台注入 / 注册面可达（§0）。
2. **基础纪律在场核验**（S1）：注入副本或技能副本 + `zxc663` 自检。
3. **能力发现**：S0 清单扫描 + 能力检索（核心 SKILL §2.1：命中即用 / 未命中才自写并归因）。
4. **按层装载**（S2/S3 按需）：渐进 vs 完整读取分类按 §4。
5. **缝合与归因**：按 §9.4 契约对接；用完不驻留；使用记归因（§9.5）。

### 9.4 缝合契约（六硬字段）+ 接入模板

| 字段 | 内容 | 判定 |
|---|---|---|
| 依赖声明 | 假设 S1 在场？不在场时的降级行为 | 必填 |
| 回指 | 指向基础技能（名称 / 位置） | 必填 |
| 仲裁位 | 「不覆盖纪律层」；冲突按仲裁序 | 必填 |
| 出口交门 | 产出落点（GATE / 承载 / 交付五查） | 家族包必填；外来技能可 N/A |
| 单一源 | 不重复定义纪律层（防棘轮） | 必填 |
| 归因 | 使用记录落点（caps= / 流水 / 账本） | 必填 |

档位自适应（禁为填表而填表）：家族包=六字段全；外来技能=最小三（依赖 / 回指 / 仲裁位），其余 N/A 声明即可；一次接入一次填写，不建登记册。

接入模板（贴入技能头部或 references 首节）：

```markdown
### 技能接入声明（与「基础纪律技能（basic skill）」同场使用时）
- 依赖声明：本技能【假设 / 不假设】基础纪律在场；不在场时 →【降级行为 / 自含照常】。
- 回指：基础技能 =【名称 / 位置】。
- 仲裁位：本技能不覆盖纪律层；冲突按仲裁序。
- 出口交门：【产出进入 GATE / 承载 / 交付五查 / 不适用】。
- 单一源：本技能不重复定义纪律层条款。
- 归因：使用记入【caps= / 流水 / 账本】。
```

### 9.5 使用归因 / 追溯（零新字段）

① GATE `caps=`（既有字段，不改 12 字段定版）记「用了哪些能力 / 技能」；② agent-log 流水行加「技能账」一要素（用了哪些技能、哪层、出口产物）；③ 产品包在场 → 其 `decision-ledger` 记裁决（§8 三缝合点照旧）。追溯效果：任一交付可回答「哪些技能参与了、各自出口落在哪、冲突怎么裁的」。
