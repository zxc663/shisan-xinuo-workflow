# layer-stack · 产品层级栈 L0-L10 与层级门（方向控制）

> 2026-09-23 用户定稿（修正三；design 记录=direction §十三）。**目的**：不是告诉模型正确答案，而是**强迫模型先确认自己正在回答哪一层的问题**——Agent 的能力结构天然擅长「在一个已经给定的框架里快速生成完整答案」，真正危险的地方恰恰是**框架本身有没有被正确确定**。
> **铁律**：**实现层完整性 ≠ 产品工程完整性**。Feature/Interaction/State 全绿，而 Product Object/Capability/Priority/Completeness/Operability 未确定时，不得声称产品工程完整。
> **位置**：跑道步骤 0（先于产品对象六问）——层级门 = 唯一入口动作，任何任务/动作/讨论先过本门。

## 1 层栈（判定「这是哪一层的问题」的坐标系）

| 层 | 内容 | 本包资产（已落地 / 占位） |
|---|---|---|
| **L0 产品目标** | 为什么做这个产品/模块、要达成什么结果 | **只检查陈述形态合格线，不生产**（PE≠PI；2026-09-24 v0.2.1 合格线入库=l0-l5-gate L0 子集：单值性/度量口径/KR 时间窗/工件存在性） |
| **L1 产品对象 / 页面职责** | 这个页面/对象为什么存在、承担什么 | 六问①②（`product-object.md`） |
| **L2 能力与功能** | 有哪些能力/功能 | 六问③ + 功能面盘点（步骤 1） |
| **L3 功能优先级与完整性** | 哪个最重要、能力是否完整 | 六问④⑤ + 页面级闭环八组 |
| **L4 产品运营 / 后台 / 权限 / 数据** | 谁管理、数据来源、后台操作能力、权限 | 六问⑥ + 第五类管理面 + 可运营性清单 |
| **L5 信息架构** | 信息怎么组织、功能放哪、用户怎么找到 | **结构底线机检**（2026-09-24 v0.2.1=l0-l5-gate L5 子集：导航三件套/前门可达/死端页 fail 级+组织声明/路径类型/tree testing 报告 warning 级；方案生产仍归母架构 Structure=v2） |
| **L6 交互** | 用户怎么完成（输入/时机/成功/失败/反悔/持久） | `interaction-bridge.md`（步骤 2、4） |
| **L7 状态** | 有哪些态、怎么流转、走不通怎么办 | statechart + 态/转换矩阵（步骤 3、4） |
| **L8 UI** | 长什么样（视觉/层级/过渡/密度） | 判定表难看域（手法层归各设计 Skill，本包只守底线） |
| **L9 实现** | 代码怎么落、组件/接口/数据从哪来 | registry / capability-map（步骤 6） |
| **L10 验证** | 怎么证明兑现（证据/追溯/回归） | spec-trace / 取证 / 账本回写（步骤 5、7） |

**与母架构的关系**（`docs/product-architecture.md`）：层栈是 Product Contracts 七域的**纵向细分坐标**——L0-L4 ↔ Intent/Scope/Runtime，L5 ↔ Structure，L6-L7 ↔ Interaction，L8-L9 ↔ Implementation，L10 ↔ Verification。

## 2 层级门（三段式：定位 → 检上游 → 放行/回补）

1. **定位**：先确定「我们现在到底在解决什么问题」→ 声明它属于哪一层（写出来：「这是 L8 问题」）。
2. **检上游**：从该层**逐层向上**检查是否有**已确认的答案**——L1-L4 为必查段（Product Object / Capability / Priority / Completeness / Operability）。
3. **放行/回补**：上游成立 → 允许在本层工作；未确认 → **停下回补**（回补工具=产品对象六问及两级清单），**不得越级下沉**。

**自答优先**：上游答案若已在项目工件中（product-object/契约/账本/设计档）→ 读档引用，**不打断用户**；无答案才停下问人（防过度提问毁采纳率）。

**四条纪律**：
- **不得越级下沉**：上层未确认，下层工作不得开始。
- **同层不阻塞**：同层内的工作可并行推进（防层层串行的仪式化）。
- **L0 只检查不生产**：目标由产品决策侧给定，本包检查其是否被陈述（PE≠PI）。
- **反向回补**：下游（L9/L10）发现的缺陷若根因在**被跳过的上游层** → 回补上游，禁就地打补丁（缺失是不可观测偏差）。

## 3 触发拦截表（动作/话语 → 所在层 → 上游必答 → 追问形态）

| 触发信号 | 层 | 必须已确认的上游 | 无答案时的追问 |
|---|---|---|---|
| 「放左边还是右边 / 什么颜色 / 圆角 / 字号」 | L8 | L2 该功能已确认；L3 主次角色 | 「先等一下：这个按钮对应的功能确认了吗？它在主次里是什么角色？」 |
| 写空态/加载/错误态组件或文案（EmptyState.vue） | L7-L8 | L3 完整性（边界与容量=空态产品语义） | 「这个页面的空态产品语义确认了吗——要让用户做什么，还是告诉他什么？」 |
| 新建组件（*.vue / *.tsx / *.jsx） | L9 | L1 职责归属；L2 能力归属（是否已有同职责组件）→ 0b | 「项目里是否已存在承担同一职责的组件？」先查 registry/组件目录 |
| 新建 API / 表 / 数据模型 | L9 | L4 运营（谁管理/数据来源/权限/后台操作能力） | 「谁管理这些数据？来源是什么？有没有后台操作能力？」 |
| 「加个开关 / 要不要做 X」 | L2-L3 | L1 职责句（X 属于这个页面吗）；L2 能力清单 | 「这个能力为什么属于这个页面？主功能是什么？」 |
| 「改布局 / 信息怎么摆 / 放哪一栏」 | L5 | L2/L3（能力与主次） | 「信息架构服务哪些能力？主功能占哪个位置？」（结构底线自答优先：跑 l0-l5-gate L5 子查验导航三件套/前门/死端；方案生产指向 v2） |
| 「要不要做 X / 为什么做这个产品」（根问） | L0 | —（目标由产品决策侧给定） | 查目标陈述合格线（l0-l5-gate L0 子集：主结果单值+可度量+KR 带时间窗）；未陈述→停下向决策侧要，**不代拟**（PE≠PI）；无人值守无法问时→显式声明假设+入账本，禁静默下沉 |
| 「状态怎么流转 / 走不通怎么办」 | L7 | L6 六问④出路已答 | 回补六问④ → statechart |
| 「加个动画 / 过渡」 | L8 | L7 变化语义 | 先过动画四问（频率→目的→easing→时长）：这个过渡让用户感知什么变化？ |
| 「把这个页面重做一下」（下游任务直投） | L6+ | L0-L4 全扫描 | 逐层列出未确认者 → 回补（六问）后再开工 |
| 走查/验证发现缺陷 | L10 | —（反向回补） | 根因在被跳过的上游层？→ 回补上游，禁就地打补丁 |

## 4 接口与纪律

- **跑道对应**：步骤 0a=本门；步骤 1=L2、2=L6、3=L7、4=L6/L7、5=L10、6=L9、7=L10。
- **命名纪律**（防三套 L 编号混淆）：包内裸「L+数字」=**产品层级**（本档）；风险深度写「**档0-档3**」（`judgement-table.md` §风险档位，2026-09-23 由 L0-L3 改名）；工作流判级写全称「**判级 L2-F**」。
- **机器可查（候选 14 已实现，2026-09-23）**：`product-object-gate.py` P3——工件声明层 + L1-L4 上游引用存在性（缺层/`file:` 悬空→逐层 exit 1；schema=product-object.md §6）；验收用例=负变体（缺 L3＋悬空 file）实测 exit 1。P2 主功能唯一性同门禁落地。
- **人工裁决域**：层定位本身（同一句话可能跨层）、上游「已确认」的充分性判断——须人确认或账本留痕。
