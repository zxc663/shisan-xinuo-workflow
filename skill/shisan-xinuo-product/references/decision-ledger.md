# decision-ledger · 裁决账本（记「为何这么定」，供下个会话直接复用）

> 与 ponytail-debt 的分工：debt=债务语义（记「为何没写」待收割）；本账本=**裁决语义**（记「为何这么定」直接生效）。来源：规格化 spec-trace 证据+走查结论+用户口头裁决。

## 行 schema
`日期｜裁决主题｜裁决内容（一句）｜依据（用户原话/学科出处/实测证据）｜被否候选｜影响面｜信心级`

## 条目准入五问（防膨胀，rule-optimizer 同源）
①解决什么真实冲突/症状？②下个会话在哪个动作前会用到？③与既有条目冲突吗（冲突则写关系：复用/互补/推翻）？④一行能说清吗？⑤有出处或证据吗？
默认每次收尾 ≤3 条，上限 5；确无新裁决写「本次无」。

## 写回时机（钩子③）
收尾固定动作：走查取证结论、用户裁决、风格选择（两栏分离的【风格】项）→ 追加本账本（只追加不压缩，月度 harvest 去重）。

## 与 registry 的关系
registry 组件行引用账本条目（组件的「为何这样」在账本）；账本不复制 registry 内容。

## 2026-09-22｜第一百零二轮（0.6.50）两条
- **裁决：并发模型换「线程本地连接代理（ConnProxy）+ WAL + timeout=10s」，放弃逐点补写锁**——单连接共享下写锁只能覆盖 storage 六处，routers/classifier/budget 的散写永远补不完（E1 Q1：事务跨线程合并=账实不符头源）；每线程一连接让「合并」在物理上不可能，属删除问题而非加层防护（ponytail：原生平台特性优先于自研）。代价=连接数×线程数，桌面 sidecar 规模可忽略。
- **裁决：月报 payload_json 列语义改为「AI 建议列表持久化」**（原设计注=calculator 同源指标快照，历史恒 NULL 无读者）——T4 采纳出路优先；同源指标快照若做（DJ-F7）届时开新列，不复用本列防语义双载。E5 伴生教训：**覆写式 upsert 换语义必须先回答「失败/中断时旧值去哪」**——generating 只翻状态、失败保旧 done，用例锁死。
