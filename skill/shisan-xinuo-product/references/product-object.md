# product-object · 产品对象定义（上游六问 + 两类清单）

> 2026-09-23 用户定稿（依据：四层分析——页面职责/能力清单/主次/能力完整性/可运营性；对应四处「偏移」的纠正：产品是什么≠功能怎么实现｜页面职责≠页面交互｜功能优先级≠功能完整性｜产品闭环≠前端闭环）。
> **位置**：跑道步骤 0，先于功能面盘点（步骤 1）与功能天生六问（步骤 2）。**对象级问题先答完，再谈功能级交互**——这是产品工程与交互工程的分层处。
> **边界**：**产品工程 ≠ 产品创新**。创新（该创造什么/市场机会/商业模式/增长策略）属产品决策侧，不是本包的活；本包管「既然决定做，它具体应该是什么」——核心敌人是「产品已决定，但 AI 把它做歪了」。

## 1 产品对象六问（缺答=停，不得进步骤 1）

| # | 问 | 答案形态 | 判定 |
|---|---|---|---|
| ① | **Purpose 为什么存在** | 解决什么问题、不解决什么（一句话） | 非空；与职责句不重复 |
| ② | **Responsibility 职责句** | 「X 管理/运营」形态——**不是**「展示 X 数据」 | 禁止动词=展示/显示 |
| ③ | **Capability 能力清单** | 这个页面有哪些能力（逐条，动词开头） | 非空；与步骤 1 盘点面对齐 |
| ④ | **Priority 主次** | **恰好一个主功能** + 每个能力挂产品角色（§4） | 主功能唯一；角色枚举 |
| ⑤ | **Completeness 能力是否完整** | 逐条过页面级闭环清单（§2） | 缺项=能力残缺：补，或显式裁决不做（写账本） |
| ⑥ | **Operability 能否被系统管理与运行** | 逐条过可运营性清单（§3） | 无管理路径须显式裁决「本期无后台+谁管内容」 |

## 2 能力完整性的页面级闭环清单（问⑤）

一个页面作为**产品能力**至少答完八组问题；缺项必须「补」或「显式裁决不做」：

1. **来源**：数据/内容从哪来（用户创建/导入/系统生成/第三方）？
2. **生命周期**：创建 / 编辑 / 删除（软删硬删）/ 禁用（禁用后发生什么）——各自谁可做？
3. **自助 vs 管理**：用户自己能改什么、管理员能改什么（两张清单分开）？
4. **检索与批量**：搜索 / 筛选 / 分页 / 排序 / 批量操作（有则给入口，无则裁决不做）？
5. **边界与容量**：空态（第一次打开）/ 大数据量 / 超长文本 / 并发编辑 / 权限不足——各自长什么样？
6. **定义与归属**：状态与枚举在哪定义（单一来源）、归哪个对象、由谁拥有？
7. **系统支撑**：API 是否支持、数据库是否支持、失败如何恢复（不一致时谁赢）？
8. **审计与出口**：操作审计、导出、恢复（回收站/撤销）？

## 3 可运营性清单（问⑥）

每个前台能力追问「谁管理它」，逐项给答案或显式裁决：
后台配置入口｜数据来源｜排序规则｜启停机制｜权限｜审核｜默认值｜fallback（内容缺失时显示什么）｜数据结构（存哪、schema 在哪）。

**假能力判据**：前台看得见、产品系统无人能管 = **只是 UI 上画出来了**，不是产品能力——记缺陷，禁以「画了」充「做了」。

## 4 主次分层（问④的产品角色表）

| 产品角色 | 例子 | 决定的后果 |
|---|---|---|
| 核心任务 | 查看/搜索/筛选订单 | 独占主视觉区、默认展示 |
| 业务操作 | 修改状态 | 一级入口或行内操作 |
| 辅助功能 | 导出 | 折叠 / 工具栏 |
| 高阶功能 | 批量处理 | 二级操作 + 条件出现 |
| 风险操作 | 删除/取消 | 确认 + 权限 + 不易触达（禁默认可见爆炸区） |

主次不明 = 平均对待全部功能 = 「什么都有，但什么都不重要」。

## 5 与下游的衔接

- **步骤 1**（功能面盘点）：能力清单 → 逐面盘点（含第五类管理面）。
- **步骤 2**（功能天生六问）：对**每个能力**答交互闭环——对象六问管「该有什么」，功能六问管「这个怎么完整」。
- **步骤 6**（实现）：**孤立能力检查**（判定表 0b）——页面需要 X 时先查产品状态模型/组件/后台能力，复用优先，必要时扩展并回写产品知识；为局部页面新造孤立能力=最高权重债务。
- **判定表**：J 域四条（职责句/主功能唯一/页面级闭环/假能力）为其裁决级形态。

## 6 机器可查形态（product-object-gate.py；候选 11/14 已实现）

跑道步骤 0b 的答案落成 JSON（`docs/contracts/<page>.object.json`），门禁逐项判：

| 字段 | 说明 | 判据 |
|---|---|---|
| purpose / responsibility | 六问①② | 非空；职责句禁「展示/显示」开头（J-29） |
| capabilities[] | 六问③：{name, role}，role∈五角色 | 非空；每条两键齐全 |
| main_function | 六问④ | **role=核心任务 须恰好一个且与 main_function 一致**（主功能数≠1→exit 1） |
| layers | 0a 层级门：{active, upstream{L1-L4}} | L1-L4 每层须 `file:<path>`／`brief:`／`adjudicated:` 三选一；file 引用悬空→逐层 exit 1 |
| operability[] | 六问⑥：{item, answer} | 非空；无管理路径须显式裁决在案（假能力判定 J-32） |

用法：`python product-object-gate.py --file docs/contracts/<page>.object.json`（P1-P4 分列报出）。**这是上游 L1-L4 的第一批机器判据**——「主功能数≠1」「上游引用悬空」「职责句错位」从此可 exit 1（2026-09-23 实现；selftest 两态＋试验仓语料转写验证）。
