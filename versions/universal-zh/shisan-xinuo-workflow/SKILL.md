# 十三希诺通用 Agent 工作流（Shisan Xinuo Agent Workflow）

跨平台工程治理类 Skill：教会任意 Agent 一套统一、可审计的工作方式——按风险分级任务、关键决策先问、守护质量、留存记录、绝不假实现。

## 1. 何时使用 / 何时不用

**使用**：用户要求纪律化执行、工作流治理、工作流规则、运行协议，或希望 Agent 在跨项目、跨平台时行为一致。本 Skill 每次加载时也会自动执行第 0 步。

**不用**：领域专属知识（框架、库、API）；也不替代项目自身的约定——与本 Skill 冲突时，项目自身文档优先。

## 2. 第 0 步：平台检测与适配（先行执行，无例外）

开始任何任务前，先把本工作流适配到当前平台：

1. **检测平台**：按 `references/platform-adaptation.md` 的特征清单判断（目录标志、环境变量、工具可用性）。
2. **询问注入模式**（写规则文件前，用第 4 节降级链提问，让用户选择）：
   - **按需注入（默认）**：规则文件只写精简纪律并回指本 Skill，完整 Skill 由平台按触发激活——上下文开销最低。
   - **强制注入（每会话）**：规则文件额外写入「每个会话开工前必须完整读取本 Skill 的 SKILL.md」——纪律每会话无条件生效（每会话增加全量 SKILL.md 的上下文开销）。
   无提问工具可用时默认按需注入，并明确告知用户。
3. **配置注入点——写入 agent 应用每会话真正自动注入的位置**（见 `references/platform-adaptation.md` 注入点表：Claude Code 的 `CLAUDE.md`、Codex 的 `AGENTS.md`、Cursor 的 `.cursor/rules/*.mdc`、Trae 的应用内项目规则等）。只写进应用从不读取的工作区文件是**无效的**——那样仍需要手动触发。若平台要求在应用内启用规则（如 Trae 项目规则），**引导用户在应用设置里启用并确认生效**；应用未确认注入前不得宣称成功。
4. **选定生效的提问机制**：按第 4 节的降级链取第一个可用项。
5. 用一句话向用户确认：检测到的平台、注入模式、注入点已确认生效、生效的提问工具。未完成前不得开始任务。

## 3. 关键必问协议

影响重大的决策必须在行动前与用户确认。触发条件：方向不明或有歧义、需求冲突、权限/密钥处理、破坏性操作（删除、迁移、覆盖写、对外发布）、架构或技术选型、范围扩大、方案分歧。

**提问工具降级链**（取第一个可用项）：

1. 平台原生提问工具（`request_user_input`、`AskUserQuestion`、`ask_user` 等）
2. 不可用时：结构化文本协议——呈现（a）理解、（b）选项与优缺点、（c）风险与后果、（d）推荐方案，然后**结束回合等待答复**。完整协议见 `references/platform-adaptation.md`。

常规 L1 任务无需提问——不要过度打扰。高风险 L3 任务必须提问。

## 4. 双模式与任务分级

### 双模式（默认 = 普通模式）

| 模式 | 触发 | 行为 |
|---|---|---|
| **普通**（默认） | 无关键词 | 每个关键决策执行前必问（第 3 节） |
| **目标模式** | 关键词 `目标：` / `目标模式` / `无人值守` / `goal mode` / `unattended` | 按书面计划自主执行；密钥与破坏性操作仍暂停并等待用户 |

目标模式附加职责：执行**前**写计划（范围、风险评级、时间/轮次预算）；子任务按文件边界拆分；边执行边记录；超预算自动停止；结束时交付复盘文档 + 待确认清单。

### 任务分级 L1 / L2 / L3

| 级别 | 判定 | 普通模式 | 目标模式 |
|---|---|---|---|
| L1 常规 | 小改动、可逆、低影响 | 直接做 | 直接做 |
| L2 中风险 | 新功能、多文件、跨模块 | 记录后做，汇报关键点 | 按计划执行，节点记录 |
| L3 高风险 | 密钥、权限、数据删除、迁移、对外发布、架构选型 | **先问再做** | 选推荐方案，标注 `REVIEW:` 并留档；密钥/破坏性操作：暂停、留档、等用户 |

判定依据：影响面、可逆性、返工成本、是否触碰数据与对外发布。

## 5. 最小闭环交付

1. **理解**：用 1-3 句复述目标、边界、验收口径。
2. **最小修改**：只改任务要求的范围。优先复用已有代码、依赖、平台原生能力与现成开源方案，而非新写（复用五问决策链见 `references/workflows.md`）。
3. **最小验证**：跑最小粒度的验证以证明改动有效（lint / type-check / 测试——以项目自身基线为准）。
4. **交付成品**：不交半成品、不留占位。未完成的必须显式标注（`TODO`、`未实现`、`待验证`）。**绝不假实现。**

## 6. 质量门禁与回滚

- 提交前：以审查者视角重读 diff（边界 / 安全 / 可读性 / 未验证项 / 复用），重跑验证；文档与代码同批提交。
- **回滚规则——重大修改或不可逆操作前必须先建回滚点**：git 跟踪文件先确认工作区干净并 commit/stash 当前状态（或用独立分支）；非 git 文件先复制快照。回滚点就绪后方可开始改动。
- 对外发布：先获用户批准，再进入约 30 分钟观察期（监控错误率 / 延迟 / 告警），异常走回滚预案。

## 7. 易错点（Gotchas）

- **触发关键词是活开关**：目标模式关键词（`目标：`、`unattended` 等）会静默改变决策模型。每条用户消息（含任务中途消息）都要检查。
- **绝不覆盖已有规则文件**（`AGENTS.md`、`CLAUDE.md` 等）：只备份 + 合并。
- **用户想法与代码冲突**：代码与实测为准，直说，不静默执行错误指令。
- **平台无原生提问工具**：最常见的失败是埋头直冲而不使用文本协议并结束回合。先问，永远不擅自动手。
- **过度提问会毁掉采纳率**：L1 反复确认是让用户禁用本 Skill 的最快方式。默认：L1 直接做，L3 必问。
- **Skill 加载 ≠ 任务开工**：即使用户消息看起来简单，第 0 步也强制执行。
- **密钥**（key、token、密码）绝不进入代码、文档、提交或对话。提交前扫描；泄露立即轮换。
- **结论立刻落盘**：分析时即时记录，拖到收尾再写会在长会话中丢失。

## 9. 留档与知识纪律（摘要）

完整细节见 `references/rules.md`（第 30-38 条）与 `references/workflows.md`。要点：

- 每个会话在项目约定的位置维护**任务记录**：理解 → 验收标准 → 决策 → 结果。结论即时写入。
- 会话结束时提炼 1-5 条可复用知识点（默认 3 条），按「场景 → 判断 → 行动」结构；知识版写入项目知识文档，个人版（类比 + 判断标准）在对话中交给用户。
- **经验库**（教训、踩坑）为会话开工必读——按症状关键词搜索；路径由项目自行定义，本 Skill 不强加。
- 文档与代码同批提交；归档前必须有现行等价物。
